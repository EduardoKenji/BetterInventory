## CPU and allocation findings

**Fixed: redundant queue snapshots.** During `stopping`, `quarantined` or
`reconciliation_required`, the facade built a controller snapshot every update
only to ask whether work was still active. `controller:is_busy()` already tests
the same pending operation, quarantine, auxiliary request and four workflow
conditions. Reusing it removes the table and any unnecessary wallet-summary work.
The new regression rejects any snapshot call during stop polling, checks each
busy condition in each queue state, and permits settlement only after a stop was
requested and all work is idle. It failed before the fix and passes afterward.

Five warmed batches of 10,000 calls, with collection stopped during each batch:

| Production facade with a quarantined controller | Before | After |
| --- | ---: | ---: |
| LuaJIT 2.1 interpreter, temporary bytes/call | 1,600 | approximately 0 |
| LuaJIT 2.1 interpreter, median microseconds/call | 0.348 | 0.138 |
| Lua 5.5, temporary bytes/call | 1,592 | approximately 0 |
| Lua 5.5, median microseconds/call | 1.052 | 0.288 |

The isolated warmed JIT trace optimizes away the old snapshot allocation too.
Its nearly empty-loop timings are not useful estimates of game CPU. The fix
reduces interpreted/cold-path work and makes the allocation unnecessary in all
modes; no FPS improvement is claimed. The benchmark stubs controller updates
to isolate facade polling, so these are not whole-workflow timings.

**Search scales with inventory size, not elapsed idle time.** Existing benchmarks
were exercised at 128, 512 and 2,048 items, in dim and hide modes. Larger fixtures
only change item count and allow enough 16-item warm-up slices. LuaJIT results:

| Items | Settled query, dim/hide (ms average) | Retained projection (KiB, dim/hide) |
| ---: | ---: | ---: |
| 128 | 0.06 / 0.04 | 479 / 476 |
| 512 | 0.18 / 0.12 | 1,513 / 1,481 |
| 2,048 | 0.72 / 0.64 | 5,486 / 5,472 |

These measurements exclude real native rendering and backend access. At 2,048
items, Lua 5.5 measured 3.32/3.43 ms per settled query and about 6 MiB of retained
projection data. Cold projection slices measured up to 4 ms with LuaJIT in this
fixture. The existing timer has millisecond resolution, so small/zero values are
coarse. Query bursts debounce; settled idle frames skip projection; cached
records are released on close. Linear cache size is expected retained data while
the inventory is open, not a demonstrated leak.

**View lifetime and idle work.** Five batches of 5,000 session open/close cycles
used callbacks capturing their owning views, then forced collection. No sessions
or views remained. A one-time approximately 189 KiB LuaJIT / 191 KiB Lua 5.5 heap
capacity increase after increasing the batch size remained flat across all five
batches. It must not be counted as 189 KiB leaked per batch. Existing search tests
also exercise 100 repeated open/query/close cycles, buffer reuse, index release
and teardown; reload tests check generation retirement and re-adoption.

The root idle dispatcher uses `needs_update` gates. With idle subsystem stubs it
allocates no meaningful per-call Lua storage and takes about 0.206 microseconds
in the LuaJIT interpreter (0.535 in Lua 5.5). This measures dispatcher overhead
only. Overview refresh is bounded to eight loadout widgets, reconciles on a
timer and reuses generations; it does not scan every inventory item every frame.
WKC trait data and customization overrides reuse item/generation-bound caches.
Search reordering reuses widgets and two layout buffers. Its benchmark includes
allocation inside the simulated native grid and cannot attribute all measured
temporary storage to BetterInventory.

**Other reviewed paths.** Panel/presentation polling, selection coordination,
automatic discard, Curio acquisition/consecration, backend read caches and
generation-bound callbacks already have idle gates, explicit release paths or
timeouts. Diagnostics use scalar counters and a one-second sampling interval,
not an accumulating event history. Transport consumes and clears its response,
polls at 0.15-second intervals and bounds HTML to 2 MiB. Persistent Curio receipts
and uncertain-operation fences are intentional durable state; clearing them to
reduce RAM could lose recovery information and was not done.

## Remaining performance risks and live checks

- Large inventory search still requires linear matching and retains a projection
  while open. The 2,048-item probe is acceptable evidence for this machine, not
  a universal frame-time budget or proof for arbitrarily large inventories.
- Games Lantern launches a helper through `io.popen`, reads local files and parses
  the completed HTML synchronously on the UI thread. Network transfer is
  asynchronous, but process startup/cancellation and completion can still hitch
  on slow storage or antivirus. Polling and size/time limits bound recurring
  work; this audit did not measure those OS delays or redesign the transport.
- Real font measurement, native UI passes, portrait resources, GPU memory,
  whole-process RSS and backend latency are outside the Lupa harness. Confirm
  long blessing labels at the friend's UI scale, then repeat inventory/vendor
  open/close and operative-switch cycles in game. Live acceptance of the existing
  Curio consecration work remains pending.
