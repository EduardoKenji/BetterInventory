# BetterInventory v1.9.4 Curio card visuals plan

Status: audit corrections implemented on this branch; in-game regression validation pending
Branch: `feature/1.9.4-curio-overlay-decoration-alignment`
Baseline: BetterInventory `1.9.3` on `main`
Target version: `1.9.4`
Prepared: 2026-08-07

## Outcome

Version 1.9.4 should make the existing **Show rarity colour strip** option work consistently for Curios and add an optional Darktide-native visual treatment to populated detailed Curio cards in Character Overview.

The native-look option should retain BetterInventory's useful title, four stat lines, and item-level text. It should change only the card's visual shell: use Darktide's ornate Curio inner frame and native Curio portrait geometry. It must not replace the detailed card with Darktide's information-poor native blueprint.

The current overlay alignment uses an 8 px downward adjustment for the title and all four stat rows, gives the centered title a 19 px horizontal inset with a 1 px left bias without changing its two-line height, moves the item level 16 px left and 16 px higher, moves equipped/favorite markers 10 px left, and anchors the native equipped/checkmark marker 40 px below the complete title band so it aligns with the primary toughness row after runtime synchronization. These adjustments are scoped to the native-overlay branch so the disabled appearance and ordinary inventory/vendor cards remain unchanged.

## Viability decision

Both changes are viable without new assets, asynchronous work, backend calls, or persistent state.

- The Curio colour strip already exists in BetterInventory's cloned detailed item pass template. It appears uncoloured because Darktide's native `gadget_item_slot` lifecycle colours `background_gradient` but, unlike the weapon lifecycle, does not colour `rarity_tag`.
- Darktide's native Curio card already exposes the desired `inner_frame` pass using `content/ui/materials/frames/line_thin_detailed_03`, as well as native Curio icon geometry. BetterInventory can clone those definitions into its hybrid detailed Curio blueprint.
- The work is UI-local and event-driven. No polling, timers, coroutines, purchase coordination, or saved rotation state are involved.

## Current architecture and root cause

### Character Overview Curios

`character_overview_curio_blueprint()` in `BetterInventory.lua` deliberately builds a hybrid card:

1. Clone the detailed generic Character Overview item blueprint and its rich pass template.
2. Adopt the native Curio slot size, currently `193 x 250`.
3. Use Darktide's native `InventoryViewContentBlueprints.gadget_item_slot` init, update, and destroy callbacks so item icons retain the native managed-resource lifecycle.
4. Run the result through `Layout.configure_native_item_blueprint()`.
5. Reposition BetterInventory title, Curio stats, icon, and item-level passes.

This preserves icon ownership correctly, but it combines passes and lifecycle callbacks that were not originally paired.

### Why the Curio colour strip is blank

The generic detailed item pass template contains `rarity_tag`, and `BetterInventory_layout.lua` correctly sizes it and applies the `show_rarity_tag` visibility setting.

Darktide's generic/weapon item callbacks assign the rarity colour to both `background_gradient.color` and `rarity_tag.color`. The native Curio `gadget_item_slot` callback assigns only `background_gradient.color`. Consequently, the cloned strip is visible but keeps its default uncoloured style.

This is a colour synchronization defect, not evidence that the Curio blueprint needs a second strip pass.

### Why the ornate overlay is absent

Darktide's `ItemPassTemplates.gadget_item_slot` includes a Curio-specific `inner_frame` pass with the ornate corner-line material. BetterInventory starts from the generic detailed item pass template, which has ordinary frame/corner passes but not the Curio-specific `inner_frame`.

The native Curio icon is also laid out as a centered `256 x 128` landscape portrait near the top of the `193 x 250` card. BetterInventory currently enlarges and repositions the generic icon for its own detailed layout. The new option must switch these visual definitions without removing detailed text passes.

### Coordinate contract and regression guard

Darktide's `UIWidget` pass renderer uses this order:

1. Resolve the pass alignment against its parent size.
2. Add `style.offset[1]` to the final X position.
3. Add `style.offset[2]` to the final Y position.
4. Add `style.offset[3]` to the render-layer Z position.

The axes are not inverted: index 1 is X, index 2 is Y, and index 3 is Z. The important distinction is that `offset[1]` and `offset[2]` are additive deltas after alignment; they are not always the left/top edge of the pass.

For the native Curio title, `horizontal_alignment = "center"` already computes the centered pass position. With a `193 px` card and a `155 px` title band, the renderer first computes `(193 - 155) / 2 = 19 px`. Therefore:

- The `19 px` inset belongs only in `size[1] = card_width - 2 * inset`.
- `offset[1] = -1` moves the already-centered title one pixel left.
- Using `offset[1] = inset - 1` incorrectly applies an additional `18 px` rightward shift. This was the cause of the title moving farther right in the previous build.

For top-aligned markers, positive Y moves down. The yellow circled checkmark is Darktide's native `equipped_icon` texture (`content/ui/materials/icons/items/equipped_label`); the orange symbol is BetterInventory/MyFavorites' separate compact `favorite_icon`. The native equipped badge is a live `InventoryView` pass, not a one-time static decoration: another update path can rewrite its runtime style after blueprint construction. Therefore the final native-overlay correction must run from the existing Character Overview update hook, derive the Y anchor from the live `better_inventory_curio_stat_1` pass, and clamp it below the live title bottom. The title-bottom-plus-40 px value remains the construction fallback, but the first stat row is the runtime authority because it tracks font scaling and localized wrapping. The equipped badge uses its own X correction (`offset[1] = -6` in the native-overlay branch); the favorite marker retains the separate marker X correction. The runtime hotspot must receive the same final coordinates for the favorite marker. The item level is bottom-aligned, but the same screen-space rule still applies: positive `offset[2]` moves it down, so its native-overlay Y delta must be negative when moving it higher.

Future native-overlay changes must document every coordinate as `x = offset[1]`, `y = offset[2]`, and `z = offset[3]`, identify the pass alignment, and explain whether a value is an absolute alignment result or an additive delta. Never put a centered pass's horizontal inset into `offset[1]`.

### 2. Synchronize rarity-strip colour at the shared layout boundary

Primary file: `scripts/mods/BetterInventory/BetterInventory_layout.lua`.

Implement a small bounded helper near `apply_item_customization_style()`:

1. Resolve the item through the existing `item_from_element()` helper.
2. If `widget.style.rarity_tag` and an item exist, obtain `Items.rarity_color(item)`.
3. Copy or clone that colour into `widget.style.rarity_tag.color` only during card init/data refresh.
4. Run per-item custom background colour application afterward, so a user's custom card colour remains the final authority.
5. Leave visibility exclusively under `show_rarity_tag`; colour synchronization must not force the pass visible.

Call the helper from the configured card init and `update_data` wrappers immediately before `apply_item_customization_style()`. This placement is preferred over a Character Overview-only patch because:

- it repairs any other hybrid/native Curio surface that has the same lifecycle mismatch;
- generic weapon and Curio cards remain idempotent;
- custom item background colours continue to override base rarity colour;
- equipped-item changes that invoke `update_data` are retinted without reopening the view.

Do not mutate the strip every frame. The base colour changes only when the widget receives a new item/data payload.

### 3. Compose the optional native Curio visual shell

Primary file: `scripts/mods/BetterInventory/BetterInventory.lua`.

Inside `character_overview_curio_blueprint()`:

1. Read `character_overview_use_native_curio_overlay` once while constructing the cloned blueprint.
2. When disabled, preserve the current pass set and geometry exactly.
3. When enabled, find the native `inner_frame` pass in `ItemPassTemplates.gadget_item_slot`, clone it, and append it only when the detailed pass template does not already contain `style_id = "inner_frame"`.
4. Never share or mutate the global native pass table. All inserted passes and mutable nested style tables must be deep clones.
5. Apply Darktide's native Curio icon dimensions/alignment/offset from the native pass instead of duplicating magic numbers where practical. If the runtime source does not expose a usable style table, use the verified native fallback geometry (`256 x 128`, top-centred, native vertical offset) in one named local helper.
6. Keep the current BetterInventory display-name, four Curio-stat, and item-level passes.
7. Resolve z-order explicitly. The inner frame must render above the background/icon but below all readable BetterInventory text. Raise only affected text pass offsets if their current z value is not already above the native frame.
8. Keep pointer/hotspot behavior, equipped indication, favorite marker, and managed icon lifecycle unchanged.

Prefer helper functions such as:

- `pass_by_style_id(pass_template, style_id)` if an equivalent is not already available locally;
- `clone_native_curio_inner_frame(pass_template)`;
- `apply_character_overview_curio_icon_geometry(icon_pass, native_overlay_enabled)`.

Helpers should be pure blueprint construction operations. They must not retain widget, renderer, item, or view references.

### 4. Preserve text readability within native geometry

The native frame and portrait occupy more of the upper card than BetterInventory's current shell. Validate and, if necessary, adjust only the native-overlay branch:

- Title: zero, one, and two-line modes.
- Character Overview strip toggles: melee, ranged, and Curio `rarity_tag` visibility are independent and default on.
- Curio title-to-stat spacing: all four attribute lines move down by the named Character Overview padding value; inventory and vendor Curio cards remain unchanged.
- Curio font scale: minimum `50%`, default `110%`, maximum `150%`.
- Four stat rows: no collision with portrait, inner frame, item level, or card bottom.
- Item level: remains readable and inside the native inner border.
- Long localized Curio names: retain existing wrapping/ellipsis contract.
- Name It forced two-line Curio names: remain supported.

Do not globally move Character Overview text merely to accommodate the opt-in overlay. Store alternate offsets/sizes in the enabled branch so the disabled layout remains pixel-identical.

## Lifecycle, performance, and memory safety

- Blueprint work occurs when Darktide asks BetterInventory to create an entry widget, not in the per-frame update loop.
- Rarity synchronization occurs on init and item/data replacement only. It is constant time and allocates at most one four-number colour table per event.
- `fit_curio_text()` compares bounded content/layout signatures during `InventoryView.update`, but performs word wrapping and table/string allocation only on initialization, item replacement, or a changed fitting signature.
- The native equipped-marker correction runs inside the already-installed `InventoryView.update` hook, but only inspects the small `_loadout_widgets` list and writes existing numeric offsets; it creates no tables, listeners, timers, or widget references.
- Reuse the native material path; do not load, cache, or unload textures manually.
- Continue using the native Curio init/update/destroy callbacks. BetterInventory must not assume ownership of icon render targets.
- Deep-clone native pass/style tables before modification. Mutating shared templates could leak the option into unrelated views or later widgets.
- Do not store widgets in module-level tables and do not register new event listeners. This avoids stale UI references and cleanup requirements.
- Avoid appending `inner_frame` more than once if the game or another mod already supplied it.
- Setting changes should use the existing view/layout refresh path. Do not layer new widgets over old ones in place.

There are no purchase or threading races in this feature. The relevant UI re-entrancy concern is repeated blueprint construction: every construction must start from fresh clones, be deterministic, and avoid modifying Darktide's source templates.

## Compatibility and edge cases

1. **Rarity strip disabled:** Curio strip remains hidden even though its colour is synchronized.
2. **Custom item background colour:** custom colour wins over rarity colour for both gradient and strip.
3. **No customization:** strip exactly follows `Items.rarity_color(item)`.
4. **Equipped Curio changes while view remains open:** `update_data` retints the existing widget.
5. **Missing or future rarity:** fail safely without indexing nil; retain the pass's existing fallback colour.
6. **Missing native template/pass:** log at diagnostic level if appropriate and retain the existing BetterInventory visual shell. Never prevent Character Overview from opening.
7. **Another mod changes native Curio passes:** locate by `style_id`, not array index.
8. **Inspecting another player:** preserve Inspect from Social and Inspect from Party Finder behavior.
9. **Empty/locked slot:** no detailed item is present; retain the existing native empty Curio blueprint and suppressions.
10. **Weapon cards:** no visual or behavioural regression.
11. **Native detailed Curios disabled:** the new overlay setting is greyed out and has no effect.
12. **UI scaling and aspect ratios:** verify Darktide logical-canvas behavior at common 16:9, 1440p/4K, and ultrawide resolutions.
13. **Localization expansion:** test long names and four-stat text with the largest font scale.
14. **Hot reload/setting toggle:** reopening or refreshing Character Overview must build exactly one frame and one icon pass.
15. **Coordinate regression:** centered title X is an additive `-1` delta, title width carries the horizontal inset, the native equipped/checkmark Y remains around the primary toughness row after runtime synchronization, and the bottom-aligned item level uses a negative Y delta to move higher.

### Finding 1: `native_marker_min_y` escapes its Lua local scope

Severity: high correctness defect with a latent compatibility/crash risk.

Current structure in `character_overview_curio_blueprint()`:

1. `local native_marker_min_y` is declared inside the first `if native_curio_overlay_enabled then` block, currently around line 545.
2. That block ends before native frame composition.
3. Later code around lines 608-642 reads `native_marker_min_y` while configuring equipped and favorite markers.

Lua locals are block-scoped. The later reads therefore resolve to `_G.native_marker_min_y`, not the earlier local. Under normal conditions the global is nil, silently disabling the intended minimum-Y clamp and causing these style fields to receive nil:

- `better_inventory_native_curio_equipped_min_y`
- `better_inventory_native_curio_favorite_min_y`

The yellow equipped checkmark currently appears usable only because `character_overview_native_curio_equipped_marker_y()` independently recalculates its Y position every frame. The favorite-marker fallback remains broken. If another mod happens to populate `_G.native_marker_min_y` with an unexpected value, placement becomes nondeterministic; a nonnumeric truthy value can reach `math.max` and crash widget construction.

Required correction:

1. Declare `local native_marker_min_y` once in the outer function scope before the first native-overlay conditional.
2. Assign it inside the title-layout block.
3. Keep every later read bound to that local.
4. Add a behavioral test that constructs the native-overlay Curio blueprint and verifies both marker minimum fields are numeric and derived from the title geometry.
5. Add a regression test with `_G.native_marker_min_y` deliberately populated to prove global state cannot affect the blueprint.

### Finding 2: Curio title/stat fitting runs and allocates every frame

Severity: medium performance and garbage-collection concern; not a persistent memory leak.

Before this refactor, `fit_curio_text()` was called from the Curio blueprint's `update` callback every frame. For every populated Curio it:

- resets the title font to its configured maximum;
- may call `Text.word_wrap()` repeatedly while shrinking the title;
- calls `Text.word_wrap()` again for all four stat lines;
- constructs content IDs through string concatenation;
- allocates wrapped-row tables and fitted strings through `table.concat()`;
- rewrites style offsets, heights, and content strings even when neither item nor layout changed.

With three Character Overview Curios this remains bounded, but it needlessly consumes UI-thread time and creates short-lived garbage throughout the time the view is open.

Implemented correction:

1. The Curio update path runs `fit_curio_text()` after native `update_data()` on item replacement and otherwise performs only cache-key comparisons.
2. The cache covers title/stat source strings, title/stat widths, font size, and title line limit.
3. The four stat content IDs are fixed blueprint-local arrays; no per-frame ID concatenation occurs.
4. Caches remain content-owned and bounded; no module-level widget cache was added.

Tests must count `Text.word_wrap()` calls and prove that repeated unchanged updates perform no additional wrapping, while an equipped-item change performs exactly one new fitting pass.

### Finding 3: MyFavorites icon and hotspot can diverge in Character Overview

Severity: medium interaction defect.

The native-overlay favorite callback can move `favorite_icon` after checking equipped-marker visibility. It moves the corresponding click target only when `content.better_inventory_myfavorites_hotspot_style` exists.

That runtime style reference is currently attached only by the `ViewElementGrid._create_entry_widget_from_config` hook. Character Overview creates these widgets through `InventoryView._create_entry_widget_from_config`, so its content does not receive the reference. On an equipped card the icon may move to its lower Y position while `myfav_hotspot` remains at the blueprint-time position, producing a visible icon whose clickable area is elsewhere.

Required correction:

1. In the Character Overview `create_widget()` path, after the native factory returns a widget, retain `widget.style.myfav_hotspot` in `widget.content.better_inventory_myfavorites_hotspot_style` using the same contract as the grid hook.
2. If compatibility code needs the live equipped-icon visibility callback, retain that pass callback for Character Overview as well.
3. Centralize the repeated runtime-style attachment in one helper used by both widget creation hooks.
4. Test that changing equipped/favorite state moves the icon and hotspot to exactly the same X/Y coordinates.

### Finding 4: native overlay mishandles the supported bottom-left favorite mode

Severity: medium compatibility/layout defect.

`Layout.configure_favorite_marker()` supports two coordinate systems:

- `above_rating`: right/top aligned, where positive Y moves the marker down from the top;
- `bottom_left`: left/bottom aligned, with an initial Y offset of `-5`.

The native Curio overlay currently applies its top-right title-clearance shifts and minimum-Y clamp without checking the marker's alignments. Applying a title-derived positive top coordinate to a bottom-aligned marker can move it into the lower decoration or beyond the card. Fixing Finding 1 without guarding alignment would expose the worst form of this bug because the previously nil minimum would become active.

Required correction:

1. Apply title-band minimum-Y logic only when `horizontal_alignment == "right"` and `vertical_alignment == "top"`.
2. Preserve the configured bottom-left marker geometry, or define a separate bottom-aligned correction expressed relative to the lower card edge.
3. Apply identical rules to the MyFavorites hotspot.
4. Test both favorite-marker positions with equipped and unequipped Curios and with one-line/two-line names.

### Finding 5: melee and ranged widgets share a mutable blueprint registry key

Severity: medium-low latent lifecycle defect and recommended refactor.

Both mirrored weapon categories currently register their newly constructed blueprint under `better_inventory_character_overview_weapon`. Darktide stores only `widget.type` on each widget and later looks the blueprint up again from `InventoryViewContentBlueprints[widget.type]` during update and destroy. The last weapon blueprint registered therefore supplies callbacks for both the melee and ranged widgets.

The current callbacks are nearly equivalent, and each widget's pass definition already contains its own strip visibility, so no present in-game regression has been confirmed. The design is nevertheless fragile: any future category-specific callback, setting, cleanup, or compatibility behavior becomes last-registration-wins.

Required refactor:

1. Define separate fixed keys such as `better_inventory_character_overview_melee_weapon` and `better_inventory_character_overview_ranged_weapon`.
2. Select the key from `weapon_kind` when adapting the config.
3. Keep Curio and empty-Curio keys separate as they already are.
4. Add a test proving Darktide's registry contains distinct melee/ranged blueprints and that each widget resolves its own update/destroy callbacks after both are created.

This remains bounded registry state; the current shared key does not itself create a memory leak.

### Finding 6: visual settings are construction-time snapshots

Severity: low unintended/stale-view behavior.

`configure_character_overview_rarity_strip()` reads each category setting while constructing the blueprint and captures `show_strip` in a closure. The native Curio overlay, title mode, and much of the geometry follow the same construction-time pattern. `mod.on_setting_changed()` refreshes dependency states but does not explicitly rebuild existing Character Overview widgets.

If a setting can change while Character Overview remains alive, existing cards may retain stale passes or geometry until the view is reopened. The runtime equipped-marker helper also checks the current overlay setting, so disabling the overlay in-place could stop its final correction while the old native-overlay widget remains displayed.

Implemented contract:

- The `InventoryView.update` hook tracks a monotonic visual-settings generation. When an active individual Character Overview layout observes a new generation, it calls Darktide's `_switch_active_layout()` lifecycle to destroy and rebuild the complete layout, including native resources and hotspots.
- The native-overlay marker helper uses the widget-owned construction flag, so an old widget cannot combine a newly changed setting with stale frame geometry.

Do not make only the strip visibility dynamic while leaving frame and geometry static unless that mixed lifecycle is intentional and tested.

### Finding 7: per-category strip controls remain subordinate to the global strip setting

Severity: low product-semantics concern requiring confirmation.

`Layout.configure_native_item_blueprint()` first applies the global `show_rarity_tag` visibility. The new melee/ranged/Curio functions wrap that result and can only hide an already enabled strip. Therefore enabling a Character Overview category does not show its strip when the global setting is off.

The implementation now documents and enforces `show_rarity_tag` as the global master switch. The three Character Overview settings independently hide their own category, but cannot override the global off state. Their visibility is evaluated dynamically and the active individual layout is rebuilt when any related setting changes.

### Finding 8: minor defensive and repository-hygiene follow-ups

Severity: low; implemented.

- The Curio init wrapper now checks that `overview_init` is callable before invoking it.
- Stat fitting now checks `stat_style.offset` and `stat_style.size` before writing them.
- Keep `pcall(Items.rarity_color, item)` and clone returned colour tables; this branch already handles the principal rarity-colour crash path correctly.
- `git diff --check` previously reported trailing whitespace in the plan's Baseline and Target lines. Those lines were normalized during this documentation update.

## Audit conclusion: performance, memory, crashes, and unintended behavior

### Performance

- Confirmed concern: repeated title/stat word wrapping and string/table allocation every frame.
- Negligible concern: the equipped-marker synchronizer walks only the small `_loadout_widgets` collection and performs bounded nil checks/numeric writes.
- Rarity-strip colour synchronization correctly runs only during init/data replacement and is not a per-frame cost.

### Memory lifecycle

No persistent memory leak was found:

- no new timers, coroutines, event subscriptions, or asynchronous jobs are introduced;
- no module-level table retains widgets, views, renderers, or items;
- widget-content caches are released with their owning view;
- custom blueprint registry entries are fixed in number;
- native Curio init/update/destroy callbacks continue to own icon-resource cleanup.

The current text-fitting implementation creates temporary garbage, but that is allocation churn rather than retained memory growth.

### Crash exposure

No deterministic crash was reproduced, and the complete verifier passes. Remaining latent paths are:

1. Global pollution interacting with the out-of-scope `native_marker_min_y` identifier.
2. A future or replaced native Curio blueprint lacking `init`, because the Curio wrapper calls it unconditionally.
3. A compatibility blueprint removing a stat style's `size` table before fitting.

These defensive paths are now hardened; the current native Darktide source satisfies the expected callback/style contract.

### Unintended behavior summary

- Favorite marker and click hotspot may not remain aligned in Character Overview.
- Bottom-left favorite-marker mode can receive top-aligned corrections.
- Existing Character Overview widgets may not reflect settings changed while the view remains alive.
- Shared melee/ranged blueprint registration creates a last-registration-wins callback dependency.
- Per-category strips cannot override the global rarity-strip switch.
