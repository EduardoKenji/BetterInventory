# v3.7.1 — Curio Buyer consecration and v3.7.0 fixes

Local `main` was fast-forwarded to `c2cd679` (v3.7.0); `v3.7.1` was created from that commit. This implementation has not been published, pushed, or synchronized to the installed mod.

## Behavior

- **Consecrate bought Curios to Transcendent** is enabled by default in DMF settings and the Curio Buyer widget. Automatic Curio Buyer itself remains disabled by default. Enabling the buyer therefore also authorizes crafting-material expenditure unless this new option is turned off.
- Only IDs returned by confirmed Automatic Curio Buyer purchases are enrolled. Existing inventory and manual purchases are not swept into the queue. Favorite behavior remains separate.
- The account-scoped persisted journal records each ID, owning character and purchase order. Duplicate receipts do not duplicate entries. FIFO processing finishes one Curio before moving to the next, one rarity upgrade per native request, up to rarity 5.
- Each step fetches authoritative gear, validates character ownership and GADGET type, reads the native upgrade recipe/costs, and checks account crafting-material balances. Other characters' purchased Curios retain their own ownership; changing the active operative does not retarget an entry.
- The worker uses the existing account-operation arbiter and mutation guard. Native gadget upgrades join the hook inventory. Curio validation/dispatch blocks conflicting hooked native mutations; Auto Crafter can defer read-only Curio work, while unresolved writes retain ownership.
- Work runs in a ready Morningstar or operative-selection context, outside matchmaking/loading. Turning off either option pauses execution. Completed or deleted/moved items leave the queue after a fresh inventory check.
- Healthy queued work polls every two seconds; deferred material/error states poll every thirty seconds. A blocked FIFO head pauses later entries. Notifications are deduplicated until state changes. No per-frame inventory scan or extra global update hook was added.

## Interruption handling

| Event | Handling |
| --- | --- |
| Mission/loading, character screen, account/active-character change | Invalidate the old read context; late callbacks cannot issue new upgrades. Resume from the journal in a permitted context. |
| GET never settles | Cancel the owned read and release its lease after 30 seconds; a later read can retry. This deadline never releases a POST fence. |
| Disable/reload while POST is outstanding | Stop follow-up dispatch. The native settlement observer and process-lifetime write fence remain responsible for the pending request. |
| Exit/restart after recorded purchase | Reload IDs from DMF settings and fetch current inventory/rarity before acting. |
| Exit/error during upgrade | The source rarity is saved and flushed before POST. If fresh rarity advanced, continue from that value. If it did not advance, retain the uncertain marker and do not replay that tier. |
| Insufficient materials | Keep the FIFO head; recheck later. No speculative upgrade or later-item spend. |
| Missing, deleted or differently owned item | Remove that entry without issuing an upgrade. |
| Another operation owns the arbiter | Wait; never steal its lease. |

An ambiguous attempt whose rarity does not advance requires checking the Curio at Hadron; an observed manual/native rarity advance lets the queue continue. A never-settling native request intentionally has no automatic timeout that permits another mutation. Restart can clear process-local request state, but the persisted uncertain-tier marker still prevents blind replay.

**Receipt boundary:** a process killed before the purchase response arrives has no confirmed newly acquired ID to record. The worker does not infer ownership from inventory differences or guess which item was bought. Such a purchase needs manual checking. Persistence uses DMF's immediate settings flush; it cannot guarantee recovery from OS/storage failure before the write reaches disk. No client-side implementation can make the server purchase and local file write one atomic transaction.

## P1/P2 remediation

- P1: extract the width value once, stopping at its quote/semicolon, then validate a bounded numeric percentage. This removes overlapping whitespace repetitions and preserves valid CSS declarations after the width. The original 16,000-space case now takes approximately 0.3–0.4 ms on local LuaJIT 2.1, versus roughly 1,082 ms in v3.7.0.
- P2: malformed/duplicate-normalized labels use a terminal validation error rather than the recoverable mark-schema ambiguity reason. Incompatible ambiguous assignments also fail before mark fallback. The original unknown-mark/379-point counterexample now rejects; supported uniquely mapped replacement stats still require review.

## Validation

- Full behavior runner: 58 files, 200 named cases, all passed; recursive coverage policies passed.
- New behavioral coverage exercises FIFO ordering across characters, multiple rarity steps, deduplication, default-enabled execution, materials, toggles, cancellation during gear/wallet reads, hung reads, late callbacks, POST interruption, reload/restart markers, account separation, deletion/ownership changes, invalid costs and persistence failure.
- Existing buyer test now exercises saving an actual purchase receipt under its real account/target-character IDs. Widget tests toggle the new checkbox; settings tests verify the default and dependency registration. Guard tests include gadget upgrades.
- Architecture, schema, bundle and Lua-structure validation accompany the runtime change. Native LuaJIT compilation checks all runtime modules.

Live rendering, actual material deductions, backend error shapes and cross-character crafting still need in-game acceptance. No account-changing request was issued during development. Use a controlled live purchase to verify those native boundaries before treating this as release acceptance.
