# BetterInventory v2.9.5 full-project DMF and runtime audit

Date: 2026-08-22

## Scope and assurance boundary

This audit rechecks the complete BetterInventory runtime after the v2.9.0-v2.9.4 changes, with regression avoidance as the primary constraint. It compares the installed current and retained legacy copies of Darktide Mod Framework, compares the installed current and retained legacy copies of Alf's DMF Extensions, and reviews all 79 Lua runtime sources for framework calls, hooks, asynchronous ownership, backend mutations, cancellation, retained state, allocation hot paths, redundant CPU work, and teardown.

The result is source- and harness-based assurance, not a proof about every future framework release or the engine allocator. A framework version that does not yet exist can change an undocumented contract, and Lua/engine allocators may retain reusable high-water pages even when no object leak exists. The repository verifier now makes the known compatibility assumptions executable, while a live repeated-view/automation soak remains the final test for an engine-level memory slope.

## CPU-focused follow-up methodology

The follow-up pass explicitly inventories every recurring entry point rather than treating all code reachable from `mod.update` as equally hot. It reviews the global frame callback, the two post-native view `update` hooks, all four post-native Auto Crafter `draw` registrations, every subsystem `needs_update`/`update` pair, recurring timers, registered-view/grid loops, and high-cardinality item/card callbacks. For each path it separates:

1. how often the small outer gate is entered;
2. how often scenegraph, inventory, widget, profile, or backend collections are traversed;
3. whether the steady path allocates tables, strings, closures, snapshots, or formatted text;
4. whether work sleeps when its view, feature, request, or transaction is inactive;
5. whether hook ownership makes a profiler incorrectly charge native work to BetterInventory.

The review also searches recurring functions for table constructors, `table.clone`, `table.concat`, `string.format`, sorting, promise creation, and `pairs`/`ipairs` loops. Harness checks validate call counts and wake behavior; they are more stable than microsecond timings in the test Lua VM. Actual Darktide frame time and engine allocation pressure still require the live profiler/soak described below.

## Actionable findings fixed

### 1. Release verification modeled only current DMF

Severity: medium release-assurance defect; no direct game-runtime failure.

`tests/verify.ps1` previously inspected only the installed current DMF and Alf trees. Pointing its DMF parameter at the retained legacy snapshot failed on current-only retained-template seams, so it could neither prove legacy compatibility nor distinguish an optional modern feature from a required baseline.

The verifier now accepts explicit legacy DMF and Alf paths and automatically checks the retained local snapshots when present. A shared contract checker verifies the complete BetterInventory-facing DMF API set, baseline option types, setting notifications, deferred persistence, disabled-state consumption, and template creation in both generations. Current DMF separately proves the three-part native color capability and retained-template seams. Both Alf generations prove constructor delegation, stable identity lookup, and step-size wrapper composition.

### 2. Diagnostics sampled an obsolete Curio read-counter name

Severity: low observability bug; purchasing and cancellation were unaffected.

The opt-in diagnostics sampler called `active_read_requests()`, while Automatic Curio Buyer exports `active_read_request_count()`. As a result, its once-per-second sample omitted Curio GET promises and could under-report backend work during a live performance investigation. The old test fixture reproduced the obsolete name, masking the interface drift.

Diagnostics now calls the real current interface and accepts the old plural name as a compatibility fallback for an older injected provider. The regression fixture exposes only the production method name, so the mismatch cannot silently return.

### 3. Deferred DMF persistence assumed a receiver-free function forever

Severity: low forward-compatibility risk; both installed generations currently use the receiver-free form.

Customization persistence called `dmf.save_unsaved_settings_to_file` without a receiver. That is correct for both inspected versions, but it would fail if a newer DMF converted the same public seam to method style. BetterInventory now supplies the DMF table as an extra protected-call argument. Lua ignores the extra argument in both current implementations, while a future method-style implementation receives the expected `self`. Success, delegated-nil, explicit rejection, exception, retry, and disable-flush behavior are unchanged and remain bounded to three attempts.

### 4. Quick Level Mastery alignment forced scenegraph work every vendor frame

Severity: low-to-medium CPU overhead when Quick Level Mastery is installed and Armoury/GlobalStore is open; no item or backend correctness defect.

The Credits vendor post-update alignment correctly avoided redundant position writes, but it still forced the weapon-stat scenegraph and queried three world geometry values every frame before discovering that the layout was unchanged. The alignment now performs a cheap reference/scalar signature check each frame and a complete verification once per 15 calls. A purchase-node rewrite, button replacement, size/offset change, or weapon-panel pivot change wakes the complete repair immediately; parent/canvas-only movement is caught by the bounded fallback. The one small probe table is view-owned and is cleared on unregister.

The regression harness proves that 15 stable calls perform one full geometry verification rather than 15, and that an external 20-pixel rewrite triggers an immediate verification and restores the exact centered position. This preserves the compatibility reason the recurring repair exists while removing the stable 60 Hz scenegraph cost.

### 5. Focused controller navigation allocated a temporary element list every frame

Severity: low allocation churn limited to controller-focused Inventory options.

The focused controller path constructed a three-element table on every input frame solely to disable the item grid, weapon options, and discard element. It now performs the same three guarded calls directly. Controller-target cleanup also avoids temporary empty-table fallbacks and iterates existing target arrays by numeric index. Focus acquisition/restoration, selected indices, left/right navigation, and embedded hotspot ownership are unchanged and retain their behavior test.

### 6. Inactive Auto Crafter overlay classified every post-draw view first

Severity: low CPU overhead across UI views while the status HUD was disabled or settled.

The safe post-draw overlay hooks classified the view name before checking the Auto Crafter HUD gate; the `BaseView` predicate could also read a partial third-party view before that gate. The inactive check now runs first and its bridge is reused for the remaining callback, so disabled overlay callbacks perform no class-name scan or presentation query. Class names are consumed only when already known to be strings, avoiding `tostring` conversion on the active path. The overlay remains a post-native safe hook and still reuses one widget per view, updating text and geometry only when its presentation revision changes.

## Crash, race, and backend audit state

- Darktide Lua execution is cooperative, so conventional thread-lock deadlocks are not introduced here. The relevant hazards are logical interleavings between promise settlements, view transitions, character changes, and account writes.
- Auto Crafter, manual discard, automatic discard, Automatic Curio Buyer, and external native/third-party account mutations retain shared operation ownership. No newly reachable overlapping-write path or premature owner release was found.
- Already-dispatched mutations retain their quarantine/owner until settlement. Cancellation stops newer work and invalidates reads; it does not pretend an ambiguous POST/DELETE was cancelled.
- Curio reads use context snapshots, request generations, cancellable promise ownership, bounded scan attempts, store-rotation coherence, candidate revalidation, and purchase idempotency.
- Equipment persistence retains only one active intent, rejects cross-character/view settlements, retries only confirmed idempotent failures, and retires captured item/view graphs after 120 seconds without duplicating an ambiguous write.
- Material safety remains scoped to BetterInventory-transformed cards and the primary inventory grid. It repairs malformed dynamic material values before rendering without a global renderer hook.
- Optional-mod probes and layout/content resolution remain fail-soft; account-changing paths remain fail-closed when authoritative services or protection data are unavailable.

No additional actionable crash, stale-callback mutation, account-operation race, retry loop, lock inversion, or backend serialization defect was found.

## Memory, allocation, and CPU audit state

- View, grid, session, operative-template, favorite-hook, editor-legend, item-policy, and projected-stat registries use weak ownership where object identity is the key, or explicit idempotent release where lifecycle ownership is available.
- Auto Crafter releases backend gear/wallet snapshots, catalogues, panel/controller graphs, queue/import presentation caches, transport processes, and temporary files at the appropriate settled boundary.
- Curio rotation history is capped at four accounts; pending reports are capped at eight with eight compact items each; operative slots are capped at 64; scan diagnostics and error text are bounded; owned-Curio best sets retain only the configured small number of Power values for the current pass.
- Custom item data is intentional persisted user state keyed by live gear identity and is pruned through gear/character deletion hooks. Pending deletion and persistence work is drained or bounded.
- Global `mod.update` continues to enter Character Overview, markers, customization, equipment, discard, Curio, diagnostics, and Auto Crafter only while the corresponding subsystem reports active work.
- Current-only color capability detection runs once during settings-data construction. Dual-generation verification adds no game-runtime work.
- Custom-tier settings, colors, weapon criteria, and Curio criteria remain precomputed on install/setting change. Rarity wrappers inspect only the supplied item; they do not rescan inventories, call `mod:get`, or query another mod's enabled state per card.
- The CPU follow-up adds no per-frame table, string, closure, inventory scan, or framework probe. Its Quick Level compatibility cache allocates once per compatible live view and is released with that view. The corrected diagnostic lookup runs only in the existing opt-in one-second sample.

No unbounded BetterInventory-owned collection, retained closed view, repeated full-inventory idle pass, orphaned child process, or actionable source-level memory leak was found.

## Regression evidence

The release suite contains 43 behavior-test files and 165 named cases. It covers the settings schema, modern/legacy color paths, DMF/Alf template identity, view lifecycle, material repair, loadout/Psykanium equipment safety, async cancellation, account mutation arbitration, Curio rotation and purchase revalidation, automatic/manual discard, Auto Crafter workflows, optional integrations, packaging, and runtime ownership.

v2.9.5 specifically adds or strengthens proof that:

- the installed current and legacy DMF snapshots expose every required shared mod API and baseline widget type;
- only current DMF is required to expose native color and retained-template facilities;
- current and legacy Alf wrappers both delegate the constructor chain and preserve stable setting identity;
- opt-in diagnostics count the production Curio read interface;
- deferred settings persistence passes a compatible receiver while preserving every existing bounded outcome;
- stable Quick Level alignment performs one full geometry verification per 15 calls, while an external rewrite is repaired immediately;
- inactive Auto Crafter post-draw callbacks do not inspect partial view class state or build presentation;
- focused controller navigation preserves behavior without constructing a temporary element list per frame;
- runtime structure contains no undeclared process-global assignment and the archive exactly matches the audited source manifest.

## Remaining live validation

Before publishing, repeat the established long-session soak with a minimal mod list and the compatibility-heavy list: reopen Inventory, Character Overview, vendors, Hadron, Brunt, Mod Options, mission preparation, and Psykanium; exercise character changes and controlled cancellation/settlement boundaries; then compare settled Lua memory, active promise counts, view/session counts, and BetterInventory CPU after equivalent garbage-collection intervals.

For the CPU comparison, use the same resolution, view, item count, frame cap, and Mod Performance Monitor sampling window. Measure an idle hub, stable Inventory, stable Character Overview, Requisition/GlobalStore with and without Quick Level Mastery, idle Brunt with the Auto Crafter panel, and an active automation run separately. With diagnostics enabled only for the controlled sample, stable Quick Level `alignment_queries` should be approximately one per 15 vendor updates (plus immediate repairs), not one per update. Disable diagnostics again for the final user-facing comparison because memory sampling and counters are intentionally not free.

A passing soak is no monotonic retained-object growth, no duplicate hook/widget/panel, no active-owner leak, no unsupported-context polling, and no behavior difference between legacy/current DMF beyond the intentionally absent legacy color preview.
