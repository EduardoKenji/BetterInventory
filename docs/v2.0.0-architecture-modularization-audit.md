# BetterInventory 2.0.0 architecture and modularization audit

Date: 2026-08-07  
Branch: `refactor/2.0.0-modularization-audit`  
Baseline: `1014ce0` (`main`, merge of `audit/v2.0.0`)  
Scope: architecture, responsibility ownership, module boundaries, extraction sequencing, and regression containment  
Audience: implementation agent, particularly Luna 5.6 xhigh or another agent that needs explicit global reasoning and incremental gates

## 1. Objective

Refactor BetterInventory without changing user-visible behavior so that:

- every runtime Lua source is below 100,000 bytes, with a preferred ceiling of 80,000 bytes for behavior-bearing modules;
- large modules become narrow facades or orchestrators instead of collections of unrelated systems;
- Custom Item Names and Colors, Automatic Curio Buyer, and Manual/Automatic Item Discard have explicit module boundaries and single state owners;
- hooks, promises, popups, native UI resources, and optional-mod integrations retain exactly one owner;
- the 2.0.0 correctness work remains intact throughout extraction;
- every batch can be reviewed, tested, committed, and reverted independently.

The byte limit is a useful forcing function, not the architecture itself. A 90 KB file with six unrelated state machines is still unacceptable. A 105 KB generated/declarative artifact may be temporarily safer than a runtime loader redesign, but the final plan below also brings localization below the limit.

## 2. Non-goals

Do not use this refactor to:

- redesign card visuals, settings, sorting semantics, discard eligibility, Curio purchase policy, or customization UX;
- rename stable setting IDs, localization IDs, persisted keys, widget IDs, scenegraph IDs, or event names;
- replace Darktide native icon ownership, inventory callbacks, popup dispatch, or equip flow;
- introduce a generic framework, service container, class hierarchy, event bus, or utility dumping ground;
- combine an architecture move with performance tuning unless a deterministic equivalence test already covers the changed path;
- close B40/B47 live validation by assertion; source-only tests cannot replace live Darktide evidence;
- delete compatibility fallbacks merely because the normal runtime has the dependency.

## 3. Current baseline

The runtime contains 19 Lua files. Current measured sizes are:

| `BetterInventory_layout.lua` | 147,890 | 4,201 | 90 | 0 | Card model, passes, runtime formatting, geometry, and blueprint mutation mixed |
| `BetterInventory.lua` | 132,048 | 3,034 | 45 | 27 | Bootstrap, overview UI, options, lifecycle, routing, and hook installation mixed |
| `BetterInventory_localization.lua` | 131,779 | 2,532 | 0 | 0 | Declarative size; lower behavioral risk but exceeds target |
| `BetterInventory_curio_acquisition.lua` | 97,022 | 3,129 | 105 | 0 | Under limit by little margin; scheduler, profiles, ledger, reads, purchase, reports mixed |
| `BetterInventory_item_customization.lua` | 50,530 | 1,427 | 31 | 8 | Already a separate feature, but persistence, Name It, editors, and hooks are mixed |
| `BetterInventory_data.lua` | 49,145 | 1,790 | 5 | 0 | Declarative settings; acceptable size |

Important interpretation:

- `features`, `layout`, and `BetterInventory.lua` are large because behavior and ownership are concentrated.
- localization is large because data is concentrated. It requires a loader-compatible data split, not behavioral decomposition.
- Curio acquisition is technically below 100 KB but has the highest responsibility density after the three god modules.
- Item customization is not too large by bytes, but the user's intuition is correct: its independent persistence and editor concerns deserve clearer ownership.

## 4. Existing strengths to preserve

The refactor starts from a substantially hardened 2.0.0 baseline:

- 14 behavior programs and 45 named risk cases pass.
- Every Python `assert` maps to exactly one risk case.
- Twelve critical async/destructive outcomes are branch-matrix gated.
- Runtime module references, Lua structure, schema drift, source manifest, ZIP content, and archive parity have established checks; AR-009 identifies a newly reproduced line-ending weakness in their cross-checkout determinism.
- Automatic Curio purchase requests are serialized and revalidated.
- Discard operations use a generation-owned arbiter.
- Equipment persistence retries are bounded and fail closed.
- Character Overview Curio presence changes use Darktide's full native layout rebuild.
- View/session ownership and several runtime caches use weak keys.
- Package discovery automatically includes root-level `BetterInventory*.lua` files.

Architecture work must preserve these safeguards rather than temporarily bypass them.

## 5. Primary architectural findings

### AR-001: `BetterInventory_features.lua` is six systems behind one facade

Current responsibility clusters include:

1. inventory/controller navigation state;
2. pass templates and scalable inventory-options panel construction;
3. Lantern and ItemSorting integrations;
4. Armoury/vendor sorting panels and comparator ownership;
5. discard eligibility and protection policy;
6. manual discard popup/transaction lifecycle;
7. automatic discard read, revalidation, confirmation, and deletion lifecycle;
8. panel positioning, visibility, settings synchronization, and teardown.

The module owns weak view registries, perfect-roll caches, panel definitions, discard transaction state, and automatic-discard state. These lifetimes are unrelated. A change to a checkbox pass can currently conflict with a destructive transaction change in the same file.

### AR-002: `BetterInventory_layout.lua` mixes model, presentation, and view geometry

Current clusters include:

1. constants and label catalogs;
2. item/trait normalization and compact descriptions;
3. weapon modifier projection and Curio value formatting;
4. content-pass factories;
5. native/custom blueprint mutation;
6. item-name and customization styling;
7. text fitting and runtime cache invalidation;
8. slot/view classification, columns, widths, and expanded view definitions;
9. inventory, Armoury, Hadron, and GlobalStore special cases.

The file's largest approximate spans include 471 lines for `configure_item_blueprint`, 310 for `configure_native_item_blueprint`, and 244 for custom pass construction. Moving only arbitrary line ranges would create hidden cross-module state and fragile helper imports.

### AR-003: `BetterInventory.lua` is not a bootstrap

It loads modules and owns DMF lifecycle callbacks, but it also contains:

- Character Overview weapon and Curio blueprint construction;
- native Curio overlay geometry and reconciliation;
- option dependency refresh/binding;
- color preset/reset handling;
- optional-mod discovery;
- grid configuration and view classification;
- 27 hook registrations across inventory, vendor, overview, gear, main menu, and grid classes;
- GlobalStore normalization and MyFavorites/Equipped Icon+ marker synchronization.

The main file should coordinate installers and lifecycle services. It should not know the internal pass structure of an equipped Curio card.

### AR-004: Automatic Curio Buyer is cohesive as a feature but not internally modular

`BetterInventory_curio_acquisition.lua` owns one large mutable `state`, which is a good single-owner property, but that state supports several separable domains:

- active context and scheduling;
- account-scoped rotation ledger;
- profile discovery and static character-slot settings;
- promise ownership and request metrics;
- store fetch/boundary normalization;
- offer normalization and eligibility;
- purchase revalidation and POST serialization;
- bounded deferred reports.

The danger is splitting the state table among modules. The correct design keeps one orchestrator state owner and extracts pure/state-specific collaborators with explicit inputs and outputs.

### AR-005: Discard policy and discard execution are coupled

Pure questions such as “is this item eligible?” share a file with irreversible backend deletion, popup ownership, view flags, and automatic scheduler tokens. This makes policy tests load UI and transaction machinery and makes state-machine edits touch large unrelated regions.

### AR-006: Item customization is a feature facade with three internal products

`BetterInventory_item_customization.lua` already isolates Custom Item Names and Colors from the main module, but it still combines:

- record normalization, CRUD, dirty state, and bounded DMF persistence;
- Name It ownership/import/reconciliation;
- popup color/name editors and input widgets;
- eight hook registrations and active-view refresh;
- gear/character deletion cleanup.

These boundaries should become explicit while retaining one public facade used by `Layout` and `BetterInventory.lua`.

### AR-007: Localization exceeds the byte target but is not a god module

The file consists of the English localization table, a `zh_cn` overlay, generated character-slot labels, and merge logic. Splitting it is valuable for size and edit conflict reduction, but it must preserve DMF's fixed `BetterInventory_localization.lua` entry point and the standalone schema/test loaders.

### AR-008: Test and packaging contracts are coupled to current filenames

The extraction must update:

- `tests/coverage_policy.json` for every new behavior module;
- `tests/case_manifest.json` if assertions move between test programs;
- `tests/branch_matrix.json` when critical ownership moves;
- `tests/check_lua_structure.py`, which currently names main/layout explicitly;
- `tests/verify.ps1`, which reads several files and checks source text;
- production-facing Lupa fixtures whose `io_dofile` stubs match module names;
- `tools/schema_manifest.py` and localization tests if localization becomes an aggregator;
- generated runtime and settings manifests;
- tracked `BetterInventory.zip`.

A refactor is incomplete if runtime behavior passes but verification silently stops inspecting the moved code.

### AR-009: Runtime hashes are checkout-line-ending dependent

This audit reproduced a clean-tree verification failure immediately after
switching from `audit/v2.0.0` to merged `main` and creating the refactor branch:

- Git reported no runtime modifications.
- Most Lua working-tree files were materialized with CRLF bytes.
- `docs/generated-runtime-bundle-manifest.json` and the tracked ZIP retained LF-based byte counts/hashes.
- `tests/check_runtime_bundle.py` therefore reported a stale manifest before the behavior suite ran.
- For example, `BetterInventory.lua` was recorded as 131,490 bytes but the clean working tree contained 132,048 bytes; the content difference is consistent with line-ending materialization.

This is a reproducibility defect, not a reason to regenerate artifacts from whichever line endings happen to be active. Modularization will add many files and amplify the problem unless R00 establishes canonical runtime line endings, preferably with `.gitattributes` (`eol=lf`) and a clean-checkout test on Windows. Manifest and ZIP hashes must describe the canonical packaged bytes on every machine.

## 6. Architecture principles

### 6.1 Single owner, explicit collaborator

Each mutable resource has exactly one owner:

| Resource | Required owner |
| --- | --- |
| DMF lifecycle callbacks and installer order | `BetterInventory.lua` |
| Each Darktide hook | one installer module named in the hook ledger |
| Character Overview visual generation/rebuild state | Character Overview UI module |
| Inventory and vendor view registries | panel/sorting owners, using weak keys |
| Manual/automatic discard arbiter token and popup | discard transaction module |
| Automatic discard scheduler/read/delete state | automatic discard module |
| Curio Buyer orchestration token/context | Curio acquisition facade/orchestrator |
| Curio rotation ledger serialization | Curio ledger module |
| Customization records and persistence dirty state | customization store module |
| Name It ownership handoff | Name It adapter module |
| Card formatting caches stored on widgets | card formatting module |
| Native icon/resource destruction | Darktide/native blueprint owner unless explicitly documented |

No two modules may write the same module-local state through shared table aliases. If two systems need the value, expose a query or immutable snapshot.

### 6.2 Flat runtime module layout

Keep new runtime files directly under:

`scripts/mods/BetterInventory/`

and name them `BetterInventory_*.lua`.

Reason: the current manifest, packager, coverage runner, and verifier discover root-level `BetterInventory*.lua`. Nested folders would require a separate packaging migration and create avoidable release risk.

### 6.3 Facades are allowed; duplicate behavior is not

Keep stable public entry modules where callers already depend on them:

- `BetterInventory_features.lua`
- `BetterInventory_layout.lua`
- `BetterInventory_curio_acquisition.lua`
- `BetterInventory_item_customization.lua`

After extraction, these should validate collaborators, compose APIs, and own only cross-domain coordination. They must not retain copied fallback implementations of entire extracted state machines. Minimal fail-closed stubs are acceptable for partial/test environments.

### 6.4 No cyclic local loads

Allowed dependency direction:

```text
BetterInventory.lua
  -> feature/layout/overview/customization/curio facades
      -> domain modules
          -> contracts/pure policy modules

UI composition -> pure content/format/geometry
State orchestrator -> pure policy and persistence adapters
Pure modules -> no facade or bootstrap imports
```

Forbidden examples:

- discard module loading `BetterInventory_features.lua`;
- card content module loading `BetterInventory_layout.lua`;
- customization store loading customization facade;
- Curio ledger loading Curio acquisition orchestrator;
- optional integration adapter reaching into another module's local state.

### 6.5 Installers must be idempotent

Any module that registers hooks exposes `install(mod, dependencies)` and guards repeated installation. It must not install hooks merely because `io_dofile` evaluated the file. This makes load order explicit and reduces hot-reload duplication risk.

The install guard itself must not suppress a legitimate new module instance after DMF hot reload. Prefer DMF's hook ownership plus a mod-scoped installation marker whose lifecycle is tested. Do not use a process-global `_G` boolean without generation/version semantics.

## 8. Public contracts

The implementation agent must write module contracts before moving callers. Suggested shapes:

```lua
-- Pure policy: no module-local operation state.
DiscardPolicy.collect_candidates(mod, source_items, protection, allowed_ids)
DiscardPolicy.protection_snapshot(profile, presets, favorites)

-- One transaction owner.
DiscardTransaction.acquire(owner, view)
DiscardTransaction.attach_popup(owner, token, popup_id)
DiscardTransaction.observe_manual_settlement(promise)
DiscardTransaction.release(owner, token, reason)
DiscardTransaction.snapshot()

-- Automatic workflow owns its scheduler state.
AutomaticDiscard.begin(mod)
AutomaticDiscard.update(mod, dt)
AutomaticDiscard.cancel(reason, preserve_settlement)
AutomaticDiscard.is_busy(mod)
AutomaticDiscard.active_read_count()

-- Curio collaborators do not own orchestration tokens.
CurioProfiles.discover(context_snapshot)
CurioLedger.load(mod, account_key, now_ms)
CurioLedger.commit_boundary(mod, ledger, boundary_ms)
CurioStore.scan(snapshot, profiles, ledger)
CurioPurchase.execute(snapshot, candidates)

-- Customization store is authoritative.
CustomizationStore.get(mod, gear_id)
CustomizationStore.update(mod, gear_id, changes)
CustomizationStore.remove(mod, gear_id)
CustomizationStore.flush(force)

-- UI modules consume dependencies explicitly.
CharacterOverviewUI.new(dependencies)
CharacterOverviewHooks.install(mod, classes, overview_ui)
```

Exact syntax may differ, but APIs must expose intent rather than internal tables.

## 10. Critical invariants and edge cases

### 10.1 General lifecycle and hot reload

- `io_dofile` may return `nil`, `false`, or a partial table in tests/failed loads; facades fail closed and log once.
- `mod:hook` callbacks must call `func` exactly once on paths where the native method is required.
- `mod:hook_safe` callbacks cannot replace native return values.
- Disable/hot reload must cancel owned reads, close panels, clear controller focus, restore comparators, release Lantern ownership, and leave in-flight destructive settlement ownership intact where required.
- Weak-key registries remain weak after extraction; do not replace them with ordinary tables.
- Late callbacks capture immutable generation/account/context snapshots, not mutable state aliases.
- Strict Darktide tables may throw on absent field reads. Optional scenegraph/private fields must use guarded access.

### 10.2 Character Overview

- Empty Curio to populated Curio triggers one native full individual-layout rebuild.
- Populated to empty and rapid repeated swaps cannot loop rebuilds.
- Existing loadout registrations, callbacks, exclamation widgets, navigation, and icon cleanup remain native-owned.
- Previous item background, custom color, name, fitted stat rows, blessing/perk rows, and rarity strip never survive onto the next item.
- Weapon and Curio blueprint identities remain distinct.
- Visible Equipment checks are guarded and do not crash when absent/disabled.
- Text fitting caches invalidate on same-gear content revision and customization changes.

### 10.3 Manual discard

- Candidate policy remains fail closed on malformed items or unavailable favorite/equipped data.
- Confirmation re-fetches/revalidates the intended IDs before deletion where current behavior requires it.
- Popup cancel, ESC, external popup removal, view exit, disable, and dispatch failure each have explicit ownership outcomes.
- After Confirm, popup disappearance does not release ownership while native deletion is in flight.
- The `GearService.delete_gear_batch` hook observes the one native request; it never issues a duplicate request.
- A delayed popup callback cannot attach an old popup to a newer transaction.
- Transaction release is generation checked and idempotent.

### 10.4 Automatic discard

- Read-only inventory fetch ownership is separate from destructive transaction ownership.
- Cancelled reads are best-effort cancelled and late callbacks are inert.
- Captured IDs are revalidated against a fresh inventory/protection snapshot before deletion.
- Manual and automatic discard cannot overlap.
- Curio purchase and automatic discard busy gates remain mutually coherent.
- Confirmation-disabled mode still retains ownership through backend settlement.
- Retry count and delay remain bounded; no per-frame retry loop.
- Notifications do not claim deletion before settlement.

### 10.5 Automatic Curio Buyer

- Store refresh before backend advancement remains nonterminal and cannot consume a rotation.
- Mixed/missing per-character storefront boundaries cannot evaluate or purchase candidates.
- Exactly one coherent post-refresh pass commits a boundary.
- Purchase candidates are identity/eligibility revalidated immediately before POST.
- Account, context, entry ID, token, and read generation must all match in continuations.
- Switching character/account invalidates old reads and cannot mutate the new context.
- Purchase POSTs remain serialized; cancellation applies only to owned reads.
- Rotation history and reports remain bounded, account-scoped, schema-migrated, and sanitized.
- Deferred reports remain once-only and oldest-first.
- Character-slot cardinality remains 64 in static DMF schema while native observed capacity is bounded.
- A failure to read wallet/store/profile data cannot become an eligible purchase.

### 10.6 Custom Item Names and Colors

- Names remain single-line, whitespace-normalized, UTF-8 length bounded, and blank means reset.
- Colors are cloned and channel-clamped; callers never retain mutable aliases to stored colors.
- `mod:set(..., false)` batching and bounded DMF flush semantics remain unchanged.
- DMF's normal nil-return save is `delegated`, not retried forever; thrown/unavailable/rejected paths remain bounded and observable.
- Name It ownership transfer is authoritative only for names; BetterInventory remains sole color owner.
- Disabling one editor and enabling the other does not erase names/colors.
- Gear and character deletion remove only matching records and persist the mutation.
- Popup input widget creation remains bounded and safe when definitions/classes are unavailable.
- Existing overview, inventory, crafting, and weapon-stat widgets refresh without forcing unsafe icon ownership changes.

### 10.7 Layout/cards/panels

- Never mutate a shared native blueprint table without cloning the intended layer.
- Pass IDs and callback names remain stable where integrations inspect them.
- Native icon render-target lifecycle remains native-owned.
- GlobalStore, Armoury, inventory, Hadron, Character Overview, and crafting paths keep separate geometry rules.
- Text fitting performs no new unbounded per-frame allocations or source-string mutation.
- Widget-local cache fields are fully reset when a widget is reused for another item.
- Panel scenegraph reads remain guarded; Character Overview does not guarantee inventory-only nodes.
- Controller focus and input legends restore on exit/disable and do not duplicate on re-entry.
- ItemSorting, Lantern, MyFavorites, Equipped Icon+, Name It, and Visible Equipment remain optional and independently disable-safe.

### 10.8 Localization and settings

- `BetterInventory_localization.lua` remains the DMF entry point and returns one flat localization table.
- Duplicate English IDs across shards fail verification.
- Chinese overlays may only target existing English IDs unless explicitly documented.
- All 240 settings retain title/tooltip coverage and metadata.
- Generated character-slot labels remain present at cold start.
- Schema digest changes only when localization/settings content intentionally changes; a pure split should preserve it exactly.

## 11. Staged implementation plan

Each batch should normally be one behavior-neutral extraction commit plus one manifest/package commit if generated artifacts change. Do not combine multiple high-risk state-machine moves merely to reach the byte target faster.

## 12. Test migration rules

For each extraction:

1. Add the new module to `coverage_policy.json` before deleting old coverage responsibility.
2. Move or add test execution so real production wiring loads the new module.
3. Keep old facade tests until all callers migrate.
4. Update branch-matrix module names for critical outcomes.
5. Ensure every new assertion maps to exactly one case range.
6. Update static source checks to inspect the new owner, not merely remove the old check.
7. Add a negative fixture for unavailable/partial module load when the collaborator is optional or fail-closed.
8. Run focused tests, then `tests/verify.ps1`.
9. Regenerate runtime/settings manifests and rebuild ZIP when runtime sources change.

Do not satisfy coverage by marking a behavior module declarative. Do not reduce per-module thresholds just because moved code initially lacks test wiring.

## 14. Anti-patterns Luna must avoid

- Do not split by copying helpers into each new file.
- Do not pass the entire `Features`, `Layout`, or Curio `state` table to collaborators.
- Do not use `_G` as cross-module state storage.
- Do not register hooks at module evaluation time in multiple files.
- Do not create mutual provider setters that form hidden cycles.
- Do not retain old implementation and new implementation behind a permanent feature flag.
- Do not move source while leaving static verifier/coverage pointed at the old file.
- Do not change settings IDs, widget IDs, callback names, or persisted schemas in a behavior-neutral extraction.
- Do not infer successful backend writes from promise construction or popup closure.
- Do not release destructive ownership on UI teardown if backend deletion still owns settlement.
- Do not manually replace one Character Overview Curio widget; preserve the native full-layout lifecycle.
- Do not put all extracted code into one new 90 KB `common.lua`.
- Do not introduce nested runtime directories without first changing and proving every packager/verifier/DMF loader contract.
- Do not chase a byte target by compressing formatting or removing useful comments/tests.

## 15. Definition of done

The modularization is complete only when all conditions hold:

- `BetterInventory.lua` is a composition root, not a UI implementation file.
- `BetterInventory_features.lua` is a facade, not the owner of panels, sorting, integrations, and two destructive flows.
- `BetterInventory_layout.lua` is a facade over cohesive content/pass/formatting/geometry/blueprint modules.
- Automatic Curio Buyer has explicit profile, ledger, store, purchase, and orchestration boundaries with one mutable context owner.
- Custom Item Names and Colors has separate store, Name It, and editor modules behind one facade.
- Manual/automatic discard policy and execution have separate owners, while sharing one transaction arbiter.
- localization preserves the fixed DMF entry point while all shards remain below the size ceiling.
- every hook and mutable resource has one documented owner.
- no local-module dependency cycle exists.
- every runtime Lua file is below 100,000 bytes.
- behavior, critical outcome, schema, manifest, package, and live acceptance gates pass.
- no unresolved regression is dismissed as “probably Darktide/backend” without logs or a bounded reproduction record.
