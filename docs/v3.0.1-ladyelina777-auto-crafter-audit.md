# v3.0.1 LadyElina777 Auto Crafter audit

Date: 2026-08-26

## Conclusion

The supplied logs resolve both reported symptoms.

1. Auto Crafter did not hang and the backend did not reject a crafting request. With **Use closest fallback** disabled, the v3.0.0 run bought and deferred 172 non-matching weapons, reached the 500,000-docket acquisition cap, and stopped without ever entering Phase 3 mastery processing. This was a real fallback-off lifecycle gap.
2. The repeated crash was finite Lua-heap exhaustion while Hadron constructed its sacrifice/modify item grid. It failed while creating `entry_163` after the account grew from 527 gear items to roughly 699. BetterInventory card initialization and GodRolls' full `WeaponStats` calculation were both in the allocation call path. The evidence does not show an infinite purchase loop, recursive UI loop, or mass favoriting.

Current v3.0.1 prevents the original level-1 run and bounds the live pre-target inventory without changing acquisition semantics. The search continues to the configured Ordo-docket or optional maximum-purchase boundary, while current-run misses are processed in rolling batches and an enabled closest fallback is reserved.

## Evidence chronology

The primary session is `console-2026-08-26-12.47.20-7fbeaaed-fd2d-4117-b04f-aea33e3ca8e6.log`.

- 14:44:28: the read-only probe reports 527 gear items, 7,073,064 dockets, 87,796 plasteel, and 22,227 diamantine before the incident run.
- 14:49:04: Auto Crafter run 8 starts in `phase3_search_purchase`.
- 14:49:04–14:49:46: the log records 172 unique `purchase_result` events and 172 matching `phase3_candidate_deferred` events. `fodder=0` throughout.
- 14:49:46: `phase3_stopped` and `purchase_search_stopped` both report `reason=search_docket_cap`, `purchases=172`, and `fodder=0`.
- 14:49:49: FpsDoctor performs an adaptive GC drain from 734.5 MB to 425.4 MB. This confirms substantial transient Lua allocation but also confirms that a collector was actively running.
- 14:50:01: `CraftingView` initializes.
- 14:50:06: the engine displays `Out of memory`.
- 14:50:08: `lua_heap` reaches its fixed 1,073,741,824-byte reservation and requests another 2,097,152-byte area.
- Two fresh sessions reproduce the same heap limit at 14:51:24 and 14:52:41.
- In the later successful 15:14 session, BetterInventory probes 528 gear items. The user had therefore removed approximately 171 of the 172 purchases before or during recovery.

The event counts are internally consistent: 172 purchases, 172 confirmations, 172 deferred candidates, 345 ordered operations started/completed, zero fodder operations, and one terminal cap event.

## Root causes and fixes

### 1. Fallback-off deferred candidates had no terminal consumer

The reporter confirms that **Use closest fallback** was off. Her expectation was that misses would still be sacrificed until mastery 20 and any remainder discarded. The old deferred workflow instead waited for an exact or fallback target before processing its queue. At the cap, no target existed, so `_stop_search` left all 172 run-owned misses in inventory.

v3.0.1 now gives that state an explicit cleanup-only terminal path:

- closest finite fallback selection still has first priority when enabled;
- otherwise, configured Phase 3 plus deferred processing switches from acquisition to cleanup without selecting a final weapon;
- current-run misses are upgraded and sacrificed in the existing maximum-eight-item BetterInventory batches;
- the minimal projected prefix is used when it can reach mastery 20;
- after verified mastery 20 and claims, only remaining current-run spares are discarded;
- if the bounded fodder is insufficient, all of it is sacrificed once and the run stops without resuming purchases;
- no fallback is invented, no result is favorited, and Phase 4 does not start.

Protection remains fail-closed. Cleanup starts from an authoritative inventory refresh and destructive completion is reconciled by another refresh. Gear ID, availability, favorite/equip state, and weapon-family identity must reconcile. Extraction and discard operate only on `purchased_spares` recorded by the current run; same-family pre-existing, equipped, favorited, unrelated, missing, or drifted items are never broadened into the cleanup set. User stops and error paths do not trigger automatic destructive cleanup.

### 2. Native progression was bypassed on level 1

Darktide unlocks Hadron through Path of Trust level 4 (`pot_crafting = 4`) and exposes `omnissiah` as the hub-facility authority. Weapon-family mastery has an additional archetype/character-level predicate in `Mastery.is_mastery_unlocked`.

v3.0.0 did not verify those gates before buying. v3.0.1 now blocks every enabled crafting mutation before account-operation ownership or the first purchase when:

- the known character level is below 4;
- the native `omnissiah` facility is explicitly locked or missing from an available progression response; or
- selected-family mastery discovery reports locked.

Levels 4–29 require affirmative family-unlock discovery. Valid Psych Ward workflows remain supported when hub progression is genuinely unavailable. A deliberately purchase-only configuration remains independent because it invokes no crafting or mastery mutation.

### 3. Deferred processing permitted excessive live inventory growth

At low-level Brunt prices, the valid 500,000-docket budget allowed exactly 172 serialized purchases. The budget and optional maximum-purchase settings behaved as configured; the defect was retaining every miss until acquisition terminated.

v3.0.1 does not add an independent acquisition ceiling. The configured Ordo-docket limit, optional maximum-purchase limit, actual wallet exhaustion, or an exact match remain authoritative. Incomplete projected-stat results are ineligible as exact/fallback candidates but do not invent a lower stopping point.

Instead, Phase 3 drains misses while acquisition is still running:

- purchases remain serialized one at a time;
- fallback off makes every confirmed miss eligible for the rolling fodder queue;
- fallback on reserves exactly the current best finite candidate; when a better roll arrives, the former reservation becomes fodder;
- eight eligible misses trigger the existing authoritative upgrade/sacrifice or discard lane;
- an exact match releases any reserved fallback into the fodder queue and remains the target;
- a configured-cap fallback remains the best candidate across the entire search, not merely the latest batch;
- processed/discarded items are removed from run-owned tracking, keeping both live inventory and controller references bounded;
- terminal cleanup handles the final partial queue without selecting a weapon when fallback is off.

Darktide's service can accept at most 40 extraction IDs, but BetterInventory intentionally remains stricter at eight items per Phase 3 mutation batch. That backend request limit is not an acquisition limit.

### 4. The 172 weapons were not favorited

The user confirms that the weapons were not favorited. The log has no candidate-accepted or favorite events, and the code only favorites an exact, finite fallback, first-weapon, or reused-inventory result. Deferred misses never call `favorite_item`.

The new cleanup tests also assert zero favorites and no accepted result while proving that an unrelated pre-existing same-family weapon survives.

## Crash attribution

The complete crash dump identifies the view and allocation point:

- `_element_view_id = "crafting_mechanicus_modify_view_item_grid"`;
- `ViewElementGrid:_on_present_grid_layout_changed` is creating `widget_entry_163`;
- native `ViewElementGrid` creates a widget and alignment widget for every layout entry before scrolling;
- BetterInventory is initializing its detailed item card and resolving the displayed item name;
- GodRolls 3 is inside `check_god_roll` at line 36, constructing `WeaponStats.new` for that name;
- `WeaponStats` is expanding weapon templates and action/tweak data when the final 2 MiB allocation fails.

The supplied GodRolls 3 archive confirms that each `Items.display_name`/`weapon_lore_family_name` hook constructs a full `WeaponStats` object, clones comparing stats, previews maximum expertise, builds and sorts a five-value table, and only then decides whether to add color/stars. BetterInventory loaded as mod 3 and GodRolls as mod 46. The native weapon blueprint had already traversed that hook before BetterInventory's formatter called `Items.weapon_lore_family_name` again for the same card, causing a redundant second full projection on compatible card paths.

This is a compatibility multiplier, not proof that either mod independently leaks. The native grid's eager per-entry widget model, an already-large 527-item account, 172 new same-family items, BetterInventory's richer cards, and GodRolls' per-name stat projection jointly exhaust the fixed Lua heap. `character_cosmetics_view_improved` and `Archivum Messelina` also hook `ViewElementGrid`, but neither appears in the captured failing Lua stack. `quick_level_mastery` appears later during manual recovery and is not part of run 8.

v3.0.1 addresses both multipliers. Rolling fodder processing prevents the acquisition spike, and BetterInventory now recognizes when the native card's decorated name is the same localized weapon-family name after removing only rich-text colour tags and leading stars. It reuses the original decorated value, retaining GodRolls' visible stars/colours and avoiding the second projection. If the native text is a full store name or an unrelated third-party replacement, BetterInventory falls back to the hooked family-name function instead of guessing. BetterInventory custom names retain their existing higher priority.

This reduces duplicate allocation pressure without bypassing GodRolls or claiming to eliminate the native grid's one calculation per unique weapon. Virtualizing Darktide's shared grid remains a materially broader compatibility change and is not justified by this incident.

## Regression matrix

- Level 1 with any crafting phase enabled: blocked before purchase.
- Purchase-only low-level configuration: remains available.
- Level 4–29 mastery automation: requires affirmative native family unlock.
- Explicitly locked/missing `omnissiah`: blocked.
- Optional purchase cap disabled and large docket budget: acquisition continues strictly to the docket boundary while rolling cleanup bounds live run-owned misses.
- Exact match on purchase 41: acquired and crafted normally after five completed eight-item rolling drains.
- Finite closest fallback enabled: one best candidate survives rolling drains and is selected only at the configured acquisition boundary.
- Incomplete projections: never become fallback/favorite candidates, but continue to the configured acquisition boundary.
- Fallback disabled, deferred fodder reaches mastery 20: sacrifice the minimal current-run prefix, claim, discard current-run remainder, select/favorite/craft nothing.
- Fallback disabled, deferred fodder is insufficient: consume it once, stop at the original cap reason, and do not resume acquisition.
- Same-family pre-existing weapon beside current-run misses: preserved.
- Phase 3 disabled: cap remains non-destructive.
- Native GodRolls-decorated family name: reused with zero second family-hook call; stars/colour remain intact.
- Non-family or third-party-replaced native name: compatibility fallback invokes the hooked family resolver.
- User stop, backend rejection, identity drift, or missing authoritative adapter: fail closed without opportunistic cleanup.

## Remaining live validation

Automated tests cover the state machine, rolling ownership boundaries, an exact match after purchase 40, reserved fallback survival, and GodRolls call-count/markup preservation. A live Darktide soak should still verify rolling cleanup with fallback both on and off on an eligible level-30 character at below-20 and already-20 mastery. No runtime patch can guarantee that an account already near Darktide's fixed Lua-heap limit will render every eager item grid with every third-party card/name hook enabled.
