# BetterInventory v2.9.0 DMF/Alf compatibility and runtime audit

Date: 2026-08-21

## Scope

This audit compares the updated installed Darktide Mod Framework with its retained previous copy, compares Alf's DMF Extensions 2.0.4 with its retained previous copy, and rechecks BetterInventory's complete runtime ownership model. The review covers API compatibility, hook composition and load order, retained options state, asynchronous work, mutation serialization, cancellation, view teardown, bounded collections, idle CPU, repeated allocations, persistence writes, and regression coverage.

The updated DMF snapshot contains 107 files versus 83 in the retained copy, including 24 new paths and a substantial Mod Options rewrite. Alf 2.0.4 contains 25 files versus 19 in the retained copy, including six new paths and multiple wrappers around DMF options construction.

## External compatibility result

No direct breaking API removal was found.

- `dmf.options_widgets_data` remains available to BetterInventory's fixed operative-row presentation bridge.
- `dmf.create_mod_options_settings(self, options_templates)` remains the final shared template seam.
- Templates preserve `setting_id`; BetterInventory now prefers it over localized presentation text.
- Final-template `disabled` and `disabled_by` state is still consumed by DMF widgets.
- `dmf.save_unsaved_settings_to_file()` remains callable with no receiver and retains its nil-on-normal-delegation behavior.
- DMF still disables hooks before invoking a mod's `on_disabled`, matching BetterInventory's cleanup assumptions.
- Alf 2.0.4's `load_dmf.lua` and `step_size_value.lua` wrappers both call the constructor implementation they captured and return its result. BetterInventory's safe hook composes in either load order.
- Alf 2.0.4 preserves and repairs stable setting IDs. BetterInventory no longer depends on localized titles when those IDs are present.

The repository verifier now checks these installed DMF and Alf seams. Repository-only verification skips an absent external mod rather than pretending it was tested.

## Findings fixed

### Retained DMF template could keep stale operative rows

The new DMF options view retains `_options_templates` across view reopenings. BetterInventory previously updated raw `options_widgets_data` after delayed profile discovery, but a template generated before that discovery kept placeholder names and unavailable metadata. Reopening the same load-always view did not reconstruct it, so a game restart could be required.

BetterInventory now weakly registers only its generated operative template entries. Profile discovery updates every still-live entry in place and triggers one dependency refresh only when presentation metadata actually changes. Weak keys ensure a replaced or destroyed external template is not retained by BetterInventory.

### Redundant settings dirtiness during roster refresh

DMF's `set` marks settings dirty even when a scalar value is unchanged. BetterInventory wrote every fixed operative checkbox on every roster refresh, causing unnecessary settings-file save work after an otherwise read-only discovery.

Roster refresh now compares each current scalar first and writes only changed rows. This path is event-driven and bounded by native operative capacity, defensively capped at 64.

### Presentation dependency binding relied on localized titles

The old compatibility path matched generated settings by localized display text. That works with older DMF/Alf versions but is vulnerable to extension rewrites, duplicate labels, rich-text category names, and localization changes.

Current templates now bind by stable `setting_id` first, with localized-title matching retained only as an older-version fallback. Cardinality and row order are unchanged.

### Bulk reset lacked a final reconciliation boundary

Updated DMF emits `on_settings_reset` after its per-widget reset callbacks. BetterInventory now uses that final boundary to refresh cached animation state, diagnostic enablement, and all option dependencies. It also restores each declared color preset before deriving RGB channels, preventing callback order from leaving a reset preset marked `custom` with mismatched channels.

## Concurrency and logical race audit

Darktide Lua execution is cooperative on the main script thread, so conventional thread deadlocks are not introduced by BetterInventory. The relevant risks are overlapping asynchronous backend operations and stale promise settlement.

- Manual discard, automatic discard, Curio purchase, Auto Crafter mutation, and equipment persistence continue to use generation/token ownership and the account-operation arbiter.
- Already-dispatched destructive or purchase requests retain ownership until settlement; cancellation prevents newer queue work but does not falsely claim a native request was cancelled.
- Read promises are cancellable where supported and have bounded timeouts/retries. Late completions are rejected by generation/context checks.
- Automatic discard, Curio acquisition, and Auto Crafter remain mutually gated around account mutation.
- Loadout, mission-preparation, Psykanium, view exit, character change, mod disable, and game-state exit cleanup paths remain covered by the existing regression suite.

No new overlapping-write path, lock inversion, unbounded retry, or settlement-without-owner path was found.

## Memory and CPU audit

- View, grid, and session registries use weak ownership or explicit idempotent release.
- The new retained-template registry uses weak keys and contains only fixed operative entries.
- Curio history, pending reports, profile slots, diagnostics, caches, and queues retain their existing hard bounds.
- Backend inventory snapshots, transient item caches, controllers, queues, promise owners, and closed-view references retain explicit release paths from the earlier process-lifetime audit.
- Global `mod.update` continues to gate every subsystem through `needs_update` or active ownership. No new idle frame poll was added.
- The compatibility fixes run only during options construction, profile revision, or bulk reset. They add no inventory-card, gameplay, or idle-frame allocation.
- Repeated dependency reconciliation reuses an existing one-element `disabled_by` list while an option remains disabled, avoiding replacement-table churn in retained DMF templates.
- BetterInventory does not wrap DMF's or Alf's per-frame options update/draw paths.

No unbounded BetterInventory-owned collection, retained closed view, per-frame full inventory pass, or new process-lifetime memory slope was found in source/harness validation.

## External observations

Alf 2.0.4 performs Mod Options-only per-frame work: it scans current settings widgets for group tooltips, maintains tab/RGB widgets, and uses a normal `BaseView.draw` wrapper. It also assigns the active options view to a global debug variable. These are Alf-owned behaviors, not BetterInventory hooks or allocations. They can affect profiler attribution or retain the load-always options view, but they do not create a BetterInventory gameplay hot path. They should be reported upstream if Mod Options itself shows sustained cost or post-close retention.

## Validation

The behavior suite covers 41 test files, including settings/template compatibility, operative discovery, mutation arbitration, cancellation, view lifecycle memory, idle update gates, character overview, loadout/Psykanium equipment safety, Auto Crafter workflows, discard, Curio purchase, and release packaging.

New regression assertions prove:

- a pre-discovery retained DMF template updates after delayed discovery;
- availability metadata triggers dependency reconciliation without polling;
- repeated unchanged roster refresh performs no additional slot-setting write;
- rewritten display text still binds through `setting_id`;
- bulk reset repairs dependency state and preset/RGB consistency;
- installed DMF and Alf constructor/persistence contracts remain present.

Static/harness validation cannot prove the engine allocator returns high-water pages to the operating system. The existing long-session live-soak procedure in `process-lifetime-memory-audit-2.1.2.md` remains the final empirical check for a real retained-memory slope.
