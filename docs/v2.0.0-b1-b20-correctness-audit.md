# BetterInventory 2.0.0 B1-B20 correctness audit

Date: 2026-08-07
Branch: `audit/v2.0.0`
Reviewed range: `70fb06d` through `fa5a4bd`
Audit baseline: `70fb06d^`
Post-B20 documentation head at review start: `013362c`

## Executive verdict

B1-B20 materially improve lifecycle safety, destructive-operation ownership, packaging integrity, UI allocation behavior, documentation, and test automation. Most commits are internally coherent and preserve their stated scope. The branch is not yet ready to treat every remediated finding as closed, however.

Two implementation defects require correction before a stable 2.0.0 release:

1. B12 assumes that a successful DMF save returns `true`. The installed DMF API always returns `nil`, including on success. After the first customization mutation, BetterInventory therefore keeps persistence pending and calls the synchronous DMF save path every second indefinitely.
2. B16's GitHub workflow invokes a verifier that unconditionally requires a sibling installed DMF tree. That tree does not exist in an ordinary GitHub Actions checkout, so the new CI is locally green but not self-contained.

Three additional behavioral gaps were found around completed work:

- manual discard releases its shared destructive-operation token when the native event is dispatched, before native deletion settles;
- Character Overview detailed-card refresh uses gear ID as the effective identity and can miss same-gear content revisions;
- deferred Curio reports use a single pending slot and can overwrite an earlier undelivered report.

The reported rapid-equip symptom is consistent with Darktide's native asynchronous loadout flow. BetterInventory's B5 card-refresh patch is not on the backend write path. The symptom still deserves instrumentation and recovery handling because the game can reopen the overview from stale profile data after its three-second waiting-state timeout.

## Scope and method

The review covered:

- every commit from B1 through B20 and its surrounding production/test changes;
- all runtime Lua modules and seven Lupa test scripts;
- the PowerShell verifier, test runner, AST/schema checks, GitHub workflow, and packaging scripts;
- the installed DMF implementation used by the mod;
- the local Darktide source for inventory equip, profile refresh, waiting-state, and deletion flows;
- tracked release archive parity and the live installed BetterInventory runtime.

The installed runtime under `Content/mods/BetterInventory` was compared byte-for-byte with the branch's ten packaged Lua files and matched. This rules out an old installed script as the explanation for the observed equip behavior.

Automated validation performed during this audit:

- `python tests/run_tests.py --timeout-seconds 45 --coverage-output audit-lua-coverage.json`: passed all seven scripts;
- `python tests/check_lua_structure.py`: passed;
- `python tests/check_schema_drift.py`: passed;
- `tests/verify.ps1 -DarktideSourcePath ..\..\Darktide-Source-Code`: passed locally;

Measured Lua line coverage was 73.2% (13,408 of 18,316 measured lines). The aggregate is not a sufficient release signal because declarative localization and data files raise it substantially. Important runtime modules remain lower: `BetterInventory.lua` 46.05%, contracts 57.14%, Curio values 54.65%, Curio acquisition 65.60%, item customization 68.97%, features 73.97%, and layout 73.06%. Branch coverage is not measured.

## Detailed findings

### BI-021 — Real DMF save contract causes perpetual retry

Priority: P1
Confidence: High
Introduced by: B12 (`a7bb63d`)

`BetterInventory_item_customization.lua` clears `persistence_pending` only when `save_unsaved_settings_to_file()` returns explicit `true`. The installed DMF implementation calls its private `save_all_settings()` and returns no value. Lua therefore returns `nil` after both a successful save and an internally swallowed `Application.set_user_setting` failure.

The result is deterministic: after a customization write, a successful DMF flush is labeled `unknown`, remains pending, and is retried every second from the update hook. This creates needless synchronous settings work and misleading status forever.

Required remediation:

- model the real API as “delegated” after a non-throwing call, not “durably confirmed”;
- clear BetterInventory's periodic retry obligation after a non-throwing `nil` result and rely on DMF's own dirty flag/lifecycle saves;
- retain bounded retry only for a thrown call or unavailable API;
- add a fixture matching the actual DMF no-return contract and assert that repeated updates do not call save again;
- remove verifier text that encodes `save_result == true` as required behavior.

### BI-022 — CI is not self-contained

Priority: P1
Confidence: High
Introduced by: B16 (`6cd256a`)

The GitHub workflow checks out this repository, installs Python dependencies, and invokes `tests/verify.ps1`. The verifier unconditionally resolves DMF from `..\..\mods\dmf` and throws if three source files are absent. That sibling tree exists in the local Darktide installation but not in an ordinary Actions checkout.

The verifier also probes and invokes `py -3`, while the workflow provisions and uses `python`. The launcher may happen to exist on a Windows runner, but the workflow should use the interpreter it installed.

Required remediation:

- separate repository-owned checks from optional external-source contract checks;
- accept explicit `-DmfSourcePath` and `-DarktideSourcePath` integration inputs;
- skip external contract checks with a clear result when no source path is supplied;
- use `python` consistently or pass the interpreter path into the verifier;
- add a clean-checkout smoke job and fail when zero test scripts are discovered.

### BI-023 — Manual discard ownership ends before backend settlement

Priority: P1
Confidence: High
Pre-existing gap adjacent to: B6 and B8

On manual confirmation, BetterInventory triggers native `event_discard_items` and immediately clears its manual transaction. Native `InventoryBackgroundView.event_discard_items` may first persist local equips and then asynchronously call `delete_gear_batch`. BetterInventory neither receives nor awaits that promise.

A second manual discard, automatic discard, or buyer destructive operation can therefore start while native deletion is still in flight. Existing B8 tests prove automatic-delete settlement ownership, but the manual tests end at event dispatch and do not represent native promise lifetime.

Required remediation:

- create an owned manual delete path that exposes settlement, or add a narrow completion bridge around the native operation;
- hold shared destructive ownership through success, rejection, cancellation policy, and view teardown;
- avoid duplicate native deletion calls;
- add a deferred native-delete regression proving that all competing destructive work remains blocked until finalization.

### BI-024 — Rapid equip persistence can reopen from stale profile state

Priority: P2
Confidence: Medium
Observed behavior: old weapon sometimes appears equipped after rapid child-view exit, outer-view exit, and reopen

Darktide's child weapon view only triggers `event_inventory_view_equip_item`; the background view updates local preview tables synchronously. BetterInventory B5 then correctly renders that preview when returning to Character Overview.

The backend write does not begin until `InventoryBackgroundView.on_exit`, which invokes `_equip_local_changes()` without retaining or awaiting the returned promise. `Items.equip_slot_items` starts `ProfilesService:equip_items_in_slots`, and failures are converted to a resolved false after logging. The next background view waits on a global loadout state for at most three seconds, then can initialize from `player:profile()` even if the backend is slow. Its `event_player_profile_updated` handler updates talent markers only; it does not rebuild equipped-item state.

This supports two distinct outcomes that look identical to the user:

1. backend success arrives late, but the reopened view remains visually stale;
2. backend request fails and the server legitimately retains the old weapon.

BetterInventory does not currently initiate or modify that native write, so B5 is not the direct cause. The right first change is diagnostic and recovery-oriented, not a second equip POST.

Required remediation:

- observe the existing equip promise and record generation, slot, requested gear ID, elapsed time, and terminal true/false/throw outcome;
- reconcile a reopened Character Overview when a profile update confirms the requested gear;
- on false/failure, discard optimistic state and notify or refresh from authoritative profile;
- distinguish a three-second UI timeout from request completion;
- never send a duplicate backend write merely because the UI timed out;
- add contract tests for delayed success, false result, stale generation, close/reopen, and profile update after timeout.

Suggested in-game evidence: reproduce once with diagnostics enabled, wait ten seconds without another equip, then reopen. A late switch indicates stale UI; a persistent old weapon plus a false/error outcome indicates backend rejection.

### BI-025 — Same-gear revisions can skip detailed card refresh

Priority: P2
Confidence: High
Adjacent to: B5

The B5 change detects equipped-card changes primarily through gear ID. Darktide's native item-slot update also recognizes a same-gear content revision when the prior and current item names differ. BetterInventory's detailed blueprint update can therefore be skipped for a new object/revision with the same gear ID, preserving old detailed text, colors, or derived fields.

Required remediation:

- define item identity as gear ID plus a stable revision/content marker, with object/name fallback;
- clear and rebuild all variable card fields when that identity changes;
- add end-to-end custom-blueprint tests for same gear/new name, icon update, stat-line count changes, and unchanged-frame no-op behavior.

### BI-026 — Pending Curio reports can overwrite each other

Priority: P2
Confidence: High
Adjacent to: B4

Account state stores one `pending_report`. A later report replaces it even when the previous report has not been delivered in Morningstar. Current tests exercise a later refresh but assert only that one report remains, so they encode the lossy storage shape rather than report preservation.

Required remediation:

- use a small bounded account-scoped queue or merge compatible transaction outcomes;
- assign a stable report ID and deduplicate delivery;
- preserve chronological order and define overflow behavior;
- test two operations before Morningstar, reload, account isolation, duplicate callback, and delivery-once behavior.

### BI-027 — Generic module fallback has unsafe semantics

Priority: P2
Confidence: Medium
Adjacent to: B1, B14, and B15

`no_op_module` returns the same function for every missing method and that function returns `false`. This is safe for some command-style modules but not for every query contract. If the settings registry fails to load, `register` returns false and logs a duplicate-ID error with no IDs, while `should_refresh_dependencies` returns false and suppresses conservative dependency refreshes.

`Contracts.safe_method` also evaluates `object[method_name]` before entering `pcall`, so a throwing metamethod is not guarded by the stated capability boundary.

Required remediation:

- replace the generic fallback with typed adapters or per-module fallback tables;
- make unavailable settings registry behavior conservatively refresh dependencies;
- put property lookup and invocation inside the protected call;
- test missing, partial, throwing, and malformed module/adaptor shapes.

## Architecture and maintainability assessment

The branch adds useful seams but does not substantially reduce change-risk concentration. Runtime size remains dominated by `BetterInventory_features.lua` (~200 KB), `BetterInventory_layout.lua` (~148 KB), `BetterInventory_localization.lua` (~131 KB), and `BetterInventory.lua` (~123 KB). Curio acquisition (~89 KB) and item customization (~49 KB) each combine state, backend, lifecycle, and presentation concerns.

The next extraction sequence should follow ownership boundaries rather than file-size targets:

1. destructive operation arbiter and manual/automatic discard state machines;
2. native equip observation/reconciliation;
3. Character Overview card view model and session teardown;
4. Curio scheduler, backend operation, ledger, and reporting domains;
5. optional integration adapters;
6. settings metadata and generated runtime data/localization.

Tests are numerous but concentrated in giant scripts with one `LuaRuntime` each. A failure stops the rest of that script, the runner reports seven script results rather than individual cases, and there is no branch coverage. Future extraction should pair each new domain with small case-level fixtures and explicit terminal-state matrices.

## Release recommendation

Do not start the largest performance or source-splitting refactors first. Correct BI-021 and BI-022, close manual destructive ownership, instrument the equip symptom, and fix same-gear refresh/report queuing. These are smaller, evidence-backed changes that stabilize the behavior and test platform on which later architecture work depends.

The revised execution order is maintained in [v2.0.0-remediation-roadmap.md](v2.0.0-remediation-roadmap.md).

## Post-audit critical hotfix addendum

After this review was committed, practical testing elevated two behaviors above normal roadmap work:

- `a5c647b` and `8e6799d` fix BI-028, where a rotation-triggered Automatic Curio Buyer pass could accept an expired pre-refresh storefront, substitute the next hourly boundary, and suppress the actual refreshed offers. Stale responses now poll as a nonterminal wait without evaluating offers, consuming the rotation, or showing a false failure.
- `4e0497f` implements BI-024 equipment persistence hardening. It observes Darktide's native request, never duplicates a pending write, retries only confirmed idempotent failures with account/character guards, and reconciles a reopened overview on authoritative profile update.

Both are owner-designated P0 release gates and require in-game validation before B22 resumes. The suite now contains eight discovered behavior scripts and the package contains eleven runtime Lua files.
