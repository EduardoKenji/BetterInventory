# BetterInventory v3.2.3 full-project performance audit

Date: 2026-08-28

## Scope and assurance boundary

This pass re-audits the complete BetterInventory runtime with behavior preservation as the primary constraint. It inventories every normal and safe hook, every recurring `update`/`draw` entry point, view/session ownership, weak and strong registries, asynchronous/backend state, Auto Crafter queues, customization reconciliation, material containment, and all Equipment Text Search projection, matching, ordering, dim/hide, widget, and teardown paths.

The findings are source- and harness-backed. They cannot prove the absence of an engine allocator defect or a conflict in arbitrary future third-party code. A live long-session soak remains the final evidence for Darktide's engine-level Lua heap and hook profiler.

## Actionable findings fixed

### 1. Temporary search rank diagnostics remained in production

The exact query `health & toughness` still activated a live diagnostic path. It constructed per-item strings, emitted matching-record logs, and dumped up to 24 sorted entries. This was useful during the v3.2.0 ordering investigation but was redundant after the fix and could distort CPU/logging results for a normal user query.

v3.2.3 removes the trace generation, callbacks, branches, string construction, and log calls completely.

### 2. Settled search evaluated every clause twice

The runtime called `Query.matches` and then `Query.rank`; ranking independently re-evaluated the same bounded clauses. A combined `Query.evaluate` path now returns match and rank from one traversal. The existing public functions remain available, and equivalence tests cover empty, invalid/fail-open, scoped text, numeric, boolean, weapon partial-match, Curio primary/secondary, equipped, and item-level cases.

In the local 128-item harness, 100 settled queries improved from 36 ms before this pass to 31 ms after it (about 14%; individual runs remain subject to timer granularity). Idle work remains approximately 0.167 microseconds per gated update in that harness.

### 3. Ordinary cards queried customization storage every frame

Card blueprints reapply explicit custom colors after God Stat Checker or another UI owner repaints a card. Customized cards need that bounded reconciliation. Ordinary cards previously retained no tracking record, so every native card update repeated item resolution, setting checks, gear-ID lookup, and customization-store lookup merely to rediscover that no override existed.

The weak widget map now stores one shared negative sentinel. Ordinary cards return immediately without allocating a per-card record. Item customization changes, enabling/disabling custom colors, shading-policy changes, settings reset, and runtime cache release invalidate the map, so the next native update resolves current state exactly once. A regression performs 120 reconciliation calls and proves zero repeated provider lookups until explicit invalidation.

### 4. Repeated presentations allocated cleanup closures

Search presentation and sort configuration repeatedly registered newly created closures under the same view-session cleanup IDs. The session correctly replaced them, so this was not a retained leak, but the allocations were unnecessary. Each runtime/manager now reuses one stable callback.

### 5. Fallback source-order entries could outlive fallback sorting

Brunt's fallback comparator needs a source-position map. If a third-party/native comparator later became available, the last fallback map remained strongly keyed until view closure. Growth was bounded to one grid generation, but retention was unnecessary. The map is now cleared immediately on that transition.

### 6. Common material passes validated twice per draw

The material crash guard must validate before and after a native/third-party change callback because that callback may corrupt the material value. Most guarded texture passes have no such callback, yet they also performed both checks. Guard installation now selects a one-check closure for the common case and preserves the two-check delegated path exactly.

### 7. Minor dead/redundant branches

The search UI's hot callback rechecked an input widget after already returning when it was absent, and search entry evaluation returned a third projection value used only by the removed trace. Both were removed.

## Equipment Text Search ownership and memory result

- Per-view state is weak-keyed and explicitly released on view closure, destruction, disable, and hot reload.
- Projection caches are weak-keyed by item and are replaced/released on invalidation or view release.
- Rank results and owned-alpha state are weak-keyed and one-generation-only; settled scans clear tables in place.
- Grid reorder buffers are view-owned, double-buffered, bounded to current grid cardinality, and cleared at release. They preserve widget identity instead of rebuilding cards.
- Query memory is optional, disabled by default, cleared on operative change, and bounded to the fixed supported view-family set for the current character.
- Typing coalesces for 80 ms; parsing, rich projection, ranking, dimming, and sorting occur only after settlement. A cold cache warms at 16 items per frame; settled idle frames perform no projection or card scan.
- Search comparators read O(1) cached ranks and preserve the selected Better Inventory, ItemSorting, or native comparator as the complete tie-break hierarchy.
- Dim owns/restores only alpha values it changed. Hide reorders existing canonical widget identities rather than recreating cards.

The post-fix harness retains about 2.4 KiB after 1,000 in-place 128-item grid commits while preserving widget identity. The 100,000-frame stable search-UI benchmark reports about 0.062 KiB transient allocation. The projection/release benchmark returns below its pre-projection Lua-memory baseline after collection. These are harness observations, not engine-heap guarantees.

## Whole-project recurring-work result

- `mod.update` retains subsystem wake gates: Character Overview, markers, customization persistence, equipment persistence, discard, Curio acquisition, diagnostics, and Auto Crafter sleep when inactive.
- No normal wrapping hook targets a shared `update` or `draw`; supported view work uses narrow safe post-native hooks. The Auto Crafter overlay remains a gated safe post-draw callback.
- Character Overview and MyFavorites registries remain weak-keyed; expensive reconciliation remains dirty/generation/timer driven.
- Automatic Discard, Automatic Curio Buyer, Equipment Persistence, and Auto Crafter preserve explicit operation ownership, generation cancellation, bounded retry/queue state, and settlement cleanup.
- Auto Crafter's 30-item rolling acquisition cleanup remains bounded by the user's existing docket/purchase limits and does not alter favorite/fallback policy.
- God Stat Checker integration remains event-driven and retains only one external-mod compatibility state table; it adds no item scan.
- Profile-spawner and material compatibility remain narrow call-boundary guards without registries or polling.
- No additional unbounded collection, repeated closed-view retention, orphaned async owner, infinite retry, duplicate account mutation, or unrestricted idle inventory traversal was found.

## Regression evidence

The v3.2.3 repository suite discovers 52 behavior-test files and 178 named risk cases. New assertions prove combined search evaluation is equivalent to the former two-call contract and that uncustomized cards remain lookup-free for 120 stable updates while event invalidation restores live resolution.

Release acceptance requires the full behavior runner, coverage gates, static/package verifier, generated schema/runtime manifests, search benchmarks, deterministic ZIP verification, and a clean tracked worktree after commits.

## Remaining live validation

Use the same view, resolution, item count, frame cap, mod list, and profiler sample duration when comparing builds. Exercise repeated queries in weapon and Curio inventory, Armoury/GlobalStore, Hadron modify/sacrifice, optional Brunt search, Character Overview, mission preparation, loadout/cosmetic changes, automation start/stop, and view reopen/hot reload. Compare settled CPU and Lua memory after equivalent garbage-collection intervals; no monotonic memory slope, duplicate UI, inactive scan, or behavior change is expected.
