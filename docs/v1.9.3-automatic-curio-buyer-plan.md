## Viability audit

Decision: viable for v1.9.3 as a bounded, opt-in scheduling extension. The local Darktide source exposes the exact `MainMenuView` lifecycle needed for Operative Selection and exposes backend millisecond store boundaries through `currentRotationEnd` and offer `price.validTo`. The existing buyer already provides sequential all-character scans, final offer revalidation, target-wallet selection, cancellation tokens, and ambiguous-POST protection, so both contexts can share one coordinator without parallel purchase work.

Implemented on this branch:

- The three settings and synchronized scalable-panel controls, with the requested defaults.
- `MainMenuView` enter/exit integration plus context-specific cancellation.
- Account-scoped persisted `next_refresh_at_ms`, bounded history, backend-time gating, five-second reset grace, and a next-whole-hour fallback only when storefront metadata is absent.
- One-second idle polling with one-shot refresh arming, ledger reset only after a new boundary, and no per-frame storefront requests.
- Pending-boundary commit at terminal evaluation or first purchase dispatch, with deterministic coverage for interrupted pre-POST retry and same-rotation duplicate suppression.

Remaining release gate: perform the in-game timing and notification-visibility matrix below. In particular, verify that the native notification feed is visible in Operative Selection on the target Darktide build and confirm the exact reset boundary with diagnostic logging before enabling the optional idle watcher for general users. A trustworthy boundary remains pending during scan and revalidation; commit it when a pass completes, or immediately before the first purchase POST. This allows an interruption before spending to retry the same rotation while still preventing duplicate or uncertain spending after any POST is sent.

## Goal

Make the Automatic Curio Buyer available in the Operative Selection screen when explicitly enabled, prevent redundant scans within one Armoury rotation by default, and optionally rescan when the store rotates while the user remains idle in an eligible screen.

The implementation must preserve the existing automatic-purchase safeguards: all-character sequential storefront scans, final offer revalidation, target-character wallet selection, serialized purchase POSTs, no retry after an ambiguous POST, cancellation tokens, and ordering behind automatic discard in the Morningstar.

## Product decisions and defaults

Add these settings under `enable_automatic_curio_acquisition`:

| Setting ID | User-facing meaning | Default | Required behavior |
| --- | --- | --- | --- |
| `automatic_curio_scan_operative_selection` | Run Automatic Curio Buyer from Operative Selection | `false` | Allows entry-triggered and, when enabled separately, refresh-triggered passes while `main_menu_view` is active. |
| `automatic_curio_once_per_store_rotation` | Scan at most once per Armoury refresh | `true` | Shares one account-scoped rotation gate across Morningstar and Operative Selection. This is not a rolling 60-minute cooldown. |
| `automatic_curio_rescan_on_store_refresh` | Rescan when Armoury refreshes while this screen remains open | `false` | Arms a single pass just after the next observed store reset in either eligible context. Operative Selection also requires its context setting. |

Recommended labels/tooltips must say that the buyer spends Ordo Dockets without confirmation, scans all enabled target characters, and that Operative Selection support is off by default.

`automatic_curio_rescan_on_store_refresh` is deliberately recommended off by default. It closes the long-idle gap but can produce two purchases close together when the first scan occurs immediately before reset. That behavior is correct and should be explained in its tooltip.

If `automatic_curio_once_per_store_rotation` is disabled, retain legacy entry behavior: one pass per eligible context entry. The idle-refresh option must still run only at an observed store boundary; it must never create an interval loop.

## Current implementation findings

### Existing buyer lifecycle

`scripts/mods/BetterInventory/BetterInventory_curio_acquisition.lua` currently owns one module-local `state` table and one `processed_offer_keys` table.

- `begin_morningstar_pass(mod)` resets the generation token, profile discovery timers, scan state, and processed-offer ledger.
- `update(mod, dt, automatic_discard_busy)` only proceeds when `current_game_mode_name()` is `hub` or `hub_singleplay` and `current_character_id()` exists.
- The first ready hub observation stores `state.hub_character_id`, waits `MORNINGSTAR_DELAY` (six seconds), waits for backend readiness and automatic discard, then starts one pass.
- `context_is_current(mod, token)` currently hard-requires `is_morningstar()`.
- `scan_candidates()` fetches all profiles once and scans enabled profiles sequentially. Storefront requests are therefore already bounded to one at a time.
- `revalidate_and_purchase()` refetches each matching storefront, compares stable fields, fetches the correct target wallet, and calls `purchase_item_with_wallet()` sequentially.
- A scanned rotation boundary remains pending until the candidate queue completes or the first purchase dispatch. Leaving before that point does not consume the rotation; leaving after it does.
- `processed_offer_keys` prevents a duplicate offer POST within the current in-memory pass/session. Ambiguous POST failures remain blocked as `unknown`.
- `cancel()` invalidates asynchronous continuations by incrementing `state.token`.
- Character-profile discovery currently runs only in Morningstar and refreshes every 300 seconds.

### Existing integration points

`scripts/mods/BetterInventory/BetterInventory.lua`:

- calls both automatic systems from global `mod.update(dt)`;
- calls `CurioAcquisition.begin_morningstar_pass(mod)` when `GameplayStateRun` enters;
- cancels on `GameplayStateRun` exit and on mod disable;
- passes `Features.morningstar_auto_discard_is_busy(mod)` into buyer update;
- forwards buyer setting changes to `CurioAcquisition.on_setting_changed()` and synchronizes settings into the scalable inventory panel.

`scripts/mods/BetterInventory/BetterInventory_data.lua` owns DMF option definitions. `BetterInventory_localization.lua` owns all localization IDs. `BetterInventory_features.lua` mirrors synchronized buyer controls into the scalable inventory-options panel.

### Native Operative Selection evidence

Local Darktide source identifies Operative Selection as `StateMainMenu` with `main_menu_view`:

- `scripts/game_states/game/state_main_menu.lua`: `StateMainMenu.on_enter`, `update`, and `on_exit` own the state.
- `scripts/ui/views/main_menu_view/main_menu_view.lua`: `MainMenuView.on_enter` triggers `event_main_menu_entered`; `on_exit` tears down the view.
- The view receives profile changes through `event_main_menu_profiles_changed` and exposes the selected profile without requiring a spawned Morningstar player.
- Existing installed mods safely use `CLASS.MainMenuView` and `CLASS.StateMainMenu` hooks, confirming those DMF hook targets.

Prefer `CLASS.MainMenuView.on_enter/on_exit` safe hooks for exact visible-screen lifetime. Do not infer Operative Selection from absence of a game mode, because loading screens and other frontend states may also have no game mode.

### Native store timing evidence

`scripts/backend/utilities/offer.lua` compares backend server time directly against `offer.price.validFrom` and `offer.price.validTo`; `seconds_remaining()` confirms those values are milliseconds. `StoreFront.data.currentRotationEnd` and `StoreFront.data.catalog.validTo` may also carry rotation bounds. `StoreFront.cache_until("personal")` deliberately returns `nil`, so the implementation must not depend on that method for personal Armoury offers.

## Required scheduling model

Use one scheduler and purchase coordinator for both contexts. Do not create a second Operative Selection scanner.

```text
unsupported
   | eligible context enters
   v
observing -> waiting_for_delay -> scanning -> purchasing -> completed_for_rotation
   ^              |                |            |
   |              +--not ready-----+            +--single serialized queue
   |
   +-- idle refresh enabled and backend reset + grace reached

Any context exit, account change, disable, hot reload, or destructive filter change
increments generation token and invalidates stale GET continuations.
An already-sent purchase POST must still be reconciled and reported.
```

Replace Morningstar-specific scheduling fields with context-neutral names:

```lua
state.active_context       -- nil, "morningstar", or "operative_selection"
state.context_generation   -- increment on every context/account lifecycle change
state.entry_id             -- increment once per eligible context entry
state.entry_scan_consumed  -- prevents repeated legacy scans in one entry
state.scheduled_reason     -- "entry", "rotation_refresh", or "retry"
state.delay_elapsed
state.scan_attempts
state.started
state.rotation_in_flight
state.next_refresh_at_ms
state.scheduler_poll_elapsed
state.account_key
```

Keep profile-discovery state separate from purchase scheduling state. A profile refresh must not reset the rotation gate or re-arm a purchase pass.

## Context lifecycle

### Morningstar

1. `GameplayStateRun` enter may announce a possible context, but final readiness remains observational: game mode must be `hub`/`hub_singleplay`, selected character must exist, and backend must be ready.
2. Call a context-neutral API such as `CurioAcquisition.enter_context(mod, "morningstar")` only once per actual entry.
3. Preserve the six-second delay and automatic-discard priority. Buyer remains blocked while `Features.morningstar_auto_discard_is_busy(mod)` is true.
4. On `GameplayStateRun` exit, call `leave_context("morningstar")`; it must not cancel a newer Operative Selection context accidentally, so compare context/generation before clearing.

### Operative Selection

1. Install `mod:hook_safe(CLASS.MainMenuView, "on_enter", ...)` and `on_exit` in `BetterInventory.lua`.
2. On view enter, if `automatic_curio_scan_operative_selection` is enabled, call `enter_context(mod, "operative_selection")` after vanilla `on_enter` completes.
3. Readiness requires:
   - `Managers.ui:view_active("main_menu_view")` and a live view instance;
   - backend authentication plus store, wallet, profile, and data-service interfaces;
   - a stable account identity;
   - profile synchronization not actively replacing/deleting/selecting a profile.
4. No Morningstar `current_character_id()` requirement applies. The all-profile scanner already carries each target `character_id` explicitly.
5. On view exit or setting disable, invalidate pending work. If a purchase POST is in flight, stop later queue entries but retain/report confirmed outcomes.
6. If the user presses Start during scan/purchase, context exit wins. Never delay game entry or hook the Start action solely to keep the scan alive.

Hooking `StateMainMenu.update` every frame is unnecessary. Continue driving lightweight scheduler progress from existing `mod.update(dt)` after the view hooks establish exact context state.

## Rotation clock and persistence

### Time sources

- Use `Managers.backend:get_server_time(Application.time_since_launch())` for rotation eligibility.
- Use `Application.time_since_launch()`/accumulated `dt` for local delays, retry backoff, and scheduler polling.
- Never use OS wall clock or `os.time()` for purchase eligibility.
- Treat missing/non-numeric server time as not ready; never guess that a reset occurred.

### Resolve current rotation end

During each successful all-character scan, collect candidate rotation boundaries in this priority order:

1. numeric `storefront.data.currentRotationEnd` when in the future;
2. numeric future `offer.price.validTo` values from personal offers;
3. numeric future `storefront.data.catalog.validTo`;
4. fallback to the next whole backend-server hour only when no authoritative bound exists.

Choose the earliest sane future boundary. Log diagnostic warnings when profiles disagree materially. Reject values that are already stale beyond grace, non-finite, or implausibly distant (recommended maximum: two hours for this hourly store). A stale response at reset must trigger bounded retry, not mark a new rotation complete.

Use a small boundary grace, recommended `STORE_RESET_GRACE_MS = 5000`, before fetching after reset. This reduces the chance of receiving the expiring catalogue at exactly `HH:00:00`.

### Rotation throttle semantics

Persist `next_refresh_at_ms`, not `last_scan_at + 3600000`.

- First-ever run: eligible immediately on context entry.
- `server_now < next_refresh_at_ms`: same rotation; skip when throttle is enabled.
- `server_now >= next_refresh_at_ms + grace`: next rotation is eligible.
- After a complete successful scan, keep the newly observed future boundary pending until final candidate evaluation. For zero eligible Curios or a queue that finishes without a POST, commit it at pass completion; otherwise commit immediately before the first purchase POST.
- After all scan retries fail before a trustworthy catalogue is obtained, do not consume the rotation. Apply an in-memory retry cooldown so repeated context transitions cannot hammer backend endpoints.
- Once any purchase POST is sent, treat that scanned rotation as consumed even if later requests fail or become ambiguous.

This commit point is intentional: a crash or context transition before spending can retry the same rotation, while a transition after POST dispatch cannot repeat uncertain spending.

### Account-scoped compact schema

Use one hidden DMF setting, for example `_automatic_curio_rotation_history`:

```lua
{
    schema_version = 1,
    accounts = {
        [account_key] = {
            next_refresh_at_ms = 1786122000000,
            last_successful_scan_at_ms = 1786118760000,
            last_context = "morningstar",
            pending_report = nil,
        },
    },
}
```

Requirements:

- Derive `account_key` from authenticated local-player/backend account identity; never key cross-account history only by selected character.
- Sanitize every loaded field and fail open for scheduling only: malformed history means one safe fresh scan, not permanent suppression.
- Keep at most four account entries, ordered by last use.
- Persist only numbers, short strings, and a compact deferred report. Never persist storefronts, offers, profiles, wallets, promises, item instances, or closures.
- Cap deferred report item lines (recommended 20) and text length. Clear it immediately after successful delivery.
- Write only when rotation/report state changes, never per frame.

## Trigger arbitration

All trigger sources call one `request_pass(reason)` function.

1. Reject unsupported/ineligible context.
2. Reject when feature disabled.
3. Resolve account and server time.
4. If a scan/purchase is active, coalesce trigger into at most one pending reason; never start parallel scans.
5. If rotation throttle is on and current rotation already consumed, skip.
6. If entry mode and this `entry_id` was consumed, skip.
7. Schedule one delayed pass and record reason.

Priority: active transaction reconciliation > automatic discard in Morningstar > retry > rotation refresh > context entry. A higher-priority trigger may replace a lower pending reason but may not duplicate it.

Transitions between Operative Selection and Morningstar within the same rotation must share persisted/in-memory gate. Example: an Operative Selection pass at 17:40 blocks the Morningstar entry pass at 17:42; both become eligible after 18:00.

## Idle reset watcher

Only activate watcher when `automatic_curio_rescan_on_store_refresh` is true and current context is eligible.

- Poll scheduler state at most once per second by accumulating `dt`.
- `get_server_time` is a local backend-time estimate; do not fetch storefronts during polling.
- Before threshold: O(1) numeric comparison, no allocation, no network.
- At `next_refresh_at_ms + grace`: call `request_pass("rotation_refresh")` once and disarm until a successful scan supplies a new future boundary.
- If boundary is unknown, do not poll-fetch hourly. Allow the next context-entry scan to establish it.
- If reset occurs while automatic discard is busy in Morningstar, keep one pending pass and run after discard settles.
- If reset occurs while another buyer pass is active, coalesce; after completion, compare newly observed boundary before deciding whether any pending trigger remains relevant.

## Purchase and cancellation safety

Generalize `context_is_current(mod, token)` to validate exact `active_context`, generation, account key, enabled settings, and live context. Do not simply replace `is_morningstar()` with `is_morningstar() or main_menu_view_active()`.

Every asynchronous continuation must check:

- generation/token still matches;
- account identity is unchanged;
- context remains active and allowed by settings;
- buyer remains enabled;
- destructive filter snapshot remains valid;
- profile and target character still exist;
- offer remains active at backend server time;
- offer ID, target character, item fingerprint, price, currency, and stable Curio fields match;
- wallet owner/currency/balance remain valid;
- no offer/wallet transaction is already in flight.

Retain sequential purchase ordering. Never send two purchase POSTs concurrently, even for different character wallets, in v1.9.3. Existing simplicity and ordered wallet transaction IDs are more important than scan speed.

When cancellation happens after POST dispatch:

- no new queue item may begin;
- attached success/failure callback must remain alive;
- confirmed purchases must refresh caches and be reported;
- timeout/unknown remains blocked in `processed_offer_keys` for process lifetime;
- never retry the POST automatically.

Consider separating `scan_generation` from a tiny transaction-reconciliation record so `cancel()` cannot accidentally garbage-collect the only reference to an in-flight result chain.

## Notifications outside Morningstar

Do not assume `event_add_notification_message` is visible in Operative Selection. Validate in game.

Preferred behavior:

1. Attempt existing native notification only where a listener is known active.
2. Always emit concise diagnostic/info logging for confirmed spending.
3. If Operative Selection cannot display the notification, persist a compact pending report and deliver it on next Morningstar readiness.
4. Deduplicate report delivery by report ID; clear only after dispatch.
5. Never show a blocking popup during automatic buying unless explicitly designed later.

The report must retain target character, Curio type/value/item level, total currency spent, insufficient-funds matches, partial-failure status, and original context.

## Setting-change behavior

- Master enabled while already in eligible context: request an entry pass if rotation gate allows.
- Master disabled: invalidate GETs and queued future purchases; reconcile any sent POST.
- Operative Selection option enabled while view is open: enter that context and request pass if eligible.
- Operative Selection option disabled while there: leave/cancel only that context.
- Rotation throttle enabled: immediately respect persisted boundary; do not cancel an already-sent POST.
- Rotation throttle disabled: do not immediately rescan if current entry already consumed; apply on next context entry unless user has just enabled master/context for first time.
- Idle watcher enabled: arm against known next boundary; do not force immediate scan solely to discover a boundary.
- Idle watcher disabled: clear pending `rotation_refresh` reason, not active entry/retry work.
- Filter/target changes during scan/purchase: preserve existing fail-closed cancellation. Do not auto-rerun during same consumed rotation after partial spending.
- Diagnostic logging toggle remains non-destructive and must not cancel work.

## Race conditions and required outcomes

| Race/edge case | Required outcome |
| --- | --- |
| Main menu and Morningstar lifecycle callbacks overlap during transition | One active context/generation wins; old callbacks ignored. Rotation gate prevents duplicate pass. |
| Two triggers arrive same frame | Coalesce into one scheduled pass. |
| User enters at 17:59, reset occurs during six-second delay | Resolve server time again before scan; classify and scan only current post-reset rotation. Do not record pre-reset rotation as completed without fetching it. |
| Scan starts before reset, storefront resolves after reset | Validate returned offer/catalogue boundary. Reject stale catalogue and retry after grace. |
| Store rotates between candidate scan and purchase | Existing final storefront refetch rejects missing/changed/expired offer. |
| Different profiles report different rotation ends | Use earliest sane future bound, log mismatch, never create parallel per-profile timers. |
| Empty storefront has no offer `validTo` | Use `currentRotationEnd`/catalog bound; only then use next server-hour fallback. |
| Backend server time temporarily unavailable | Wait; no OS-time fallback and no purchase. |
| Backend clock moves backward/forward | Sanity-check persisted boundary; large impossible jumps invalidate history and require fresh safe scan. |
| User changes selected operative during menu scan | Continue only if account and target profiles remain valid; selected operative itself is not wallet authority. |
| Character deleted during scan | Final profile/offer validation excludes it; no purchase. Refresh character slots later. |
| User presses Start during GET | Cancel/ignore continuation; never delay Start. |
| User leaves after scan but before first purchase POST | Do not persist the pending boundary; next eligible context may retry same rotation. |
| User presses Start after POST sent | Stop later purchases, reconcile/report sent POST, block same rotation in Morningstar. |
| Mod disabled/hot reloaded during GET | Token invalidates callback; release captured references. |
| Mod disabled/hot reloaded after POST | Reconcile result if runtime permits; persisted consumed rotation prevents automatic same-rotation replay. |
| Purchase succeeds but client times out | Mark unknown, refresh/reconcile caches, never repeat POST. |
| Another mod/vanilla spends wallet | Final wallet fetch catches new balance; sequential queue re-fetches for each candidate. |
| No enabled Curio types/targets | Complete scan once, report according to current notification preference, persist rotation boundary. |
| Scan fails three times | No rotation consumption unless trustworthy catalogue reached; set bounded in-memory retry cooldown. |
| Settings persistence write fails | Log once, retain in-memory gate for session, fail safe against duplicate purchases. |
| Multiple local accounts use same mod config | Account-keyed history keeps schedules separate and capped. |

## CPU, network, RAM, and leak prevention

### CPU

- No storefront/profile work per frame.
- Accumulate `dt`; evaluate idle boundary at one-second cadence maximum.
- Cache context/account readiness for each poll, but revalidate before network and purchase.
- Keep rotation helpers pure and allocation-light.
- Continue rejecting non-Curios before expensive item normalization.
- Do not repeatedly rebuild character settings or panel widgets from scheduler ticks.

### Network

- At most one all-character scan active.
- Keep current sequential storefront fetches; no fan-out burst.
- Coalesce entry, setting, retry, and refresh triggers.
- Never fetch merely to ask whether reset happened; compare server time with stored boundary.
- Preserve bounded retries and add jitter only if tests show synchronized traffic is a concern.
- Final revalidation fetch remains mandatory even if it doubles request count for matched offers.

### RAM

- Keep only compact candidate records during active pass.
- Clear storefront, offer, profile, wallet, diagnostics, candidate arrays, and promise-chain references on terminal completion/cancellation when safe.
- Reset `processed_offer_keys` when entering a genuinely new rotation/account, not every context transition.
- Cap account history, diagnostics text, deferred reports, and processed-offer ledger.
- Never retain `MainMenuView` instances in module state; query weak/liveness context when needed.

### Leak prevention

- Every hook installed once; no hook installation from `update()` or setting callbacks.
- Every registered event must have paired unregister or use DMF hook lifecycle.
- Promise callbacks capture compact IDs/snapshots rather than view objects.
- Generation checks must return before mutating current state.
- In-flight POST reconciliation is the only intentional stale-generation continuation and must clear itself after terminal callback.
- Hot reload must increment generation and discard old timers, pending reasons, diagnostics, and GET chains.
