# BetterInventory 2.0.0 full-project audit

Date: 2026-08-07  
Branch: `audit/v2.0.0`  
Baseline: `854ab1c` (`main`)  
Target version: `2.0.0`  
Audit type: static code, architecture, lifecycle, async, performance, test, packaging, and local game-contract review

## Purpose and handoff contract

This document is an implementation backlog, not only a narrative review. It is written so another coding agent can address findings one at a time without rediscovering project context.

For every change:

1. Preserve the fail-closed behavior of discard and purchase workflows.
2. Add or extend a deterministic test before changing high-risk behavior.
3. Run `tests/verify.ps1` after each logical batch.
4. Keep in-game validation separate from deterministic automated acceptance criteria.
5. Do not combine architecture extraction with behavior changes unless the behavior is already covered by tests.
6. Treat Darktide and optional-mod private fields as versioned contracts. Guard them at one adapter boundary.

## Executive summary

The current baseline is unusually well defended for a Darktide Lua mod. Automated verification passes; destructive flows revalidate candidates; Curio purchases are serialized; icon ownership remains native; runtime caches use weak keys where appropriate; rotation history and retries are bounded.

No confirmed unbounded Lua-table leak or BetterInventory-owned render-target leak was found in current source. Main memory risks are stale closures after disable/hot reload, promise graphs retained until backend settlement, and avoidable allocation churn in per-frame hooks.

Release should still be treated as pre-validation. Audit found three high-risk lifecycle/async defects, one release-artifact defect, several unguarded compatibility calls, and substantial refactoring debt:

- Manual discard transaction can remain locked if confirmation closes without either option callback.
- Wrapped sort comparators are not restored on disable and can retain old module closures across hot reload.
- Cancelling automatic discard releases shared transaction ownership even when backend deletion remains in flight.
- Tracked `BetterInventory.zip` was v1.8.0 while source was v1.9.4; current verifier did not notice.
- Global grid and vendor update hooks perform avoidable per-frame allocations/scans.
- `BetterInventory_features.lua`, `BetterInventory_layout.lua`, and `BetterInventory.lua` mix too many responsibilities and contain several 200-500-line functions.
- Test volume was high but initially had no measured Lua coverage, CI workflow, or standard discovery; B16 added these foundations, with clean-checkout portability still open as BI-022.
- Several documented in-game gates remain open, especially hot enable/disable, popup cancellation, controller focus, supported-mod combinations, and Operative Selection notifications.

Independent B1-B20 review supersedes the original release ordering: fix BI-021 through BI-023, establish BI-024 diagnostics, and close BI-025/BI-026 before performance and architecture expansion.

## Post-audit P0 crash addendum

During owner validation after B40/B41 packaging, opening a melee weapon from
Character Overview crashed Darktide with:

`scripts/foundation/utilities/table.lua:1204: Table does not have field_name "window" defined.`

The direct cause was an optional geometry probe in
`BetterInventory_features.lua` reading `scenegraph.window` and
`scenegraph.canvas` through Darktide's strict scenegraph table. Character
Overview does not guarantee those inventory-only nodes during its transition.
The fix in `665801b` uses raw/protected optional-field reads, treats absent
nodes as a degraded geometry state, and covers a strict scenegraph fixture in
`tests/test_features.py`. The source and deployed runtime now match, and the
rebuilt archive is verified. B40 remains open: the crash fix still requires
the in-game melee/Character Overview retest and the remaining live matrix.

## B50 addendum — empty Curio slot lifecycle

Owner validation found a visible card-format regression that can occur before
the B42-B47 sequence: click an empty Curio slot, equip a Curio, and return to
the still-open Character Overview. The newly equipped item could appear with
Darktide's basic Curio card rather than BetterInventory's detailed card. The
same symptom occurred without custom names or colors, so customization data was
not the cause. Closing and reopening the overview rebuilt the widget and hid the
defect.

Local Darktide source confirms the lifecycle gap. Individual loadout widgets
store a fixed `widget.type`; native `gadget_item_slot.update` updates
`content.item`, icon, and native colors but does not recreate the pass template.
BetterInventory intentionally created a separate empty-slot blueprint, so an
empty→equipped transition could retain that blueprint indefinitely.

B50 adds a post-update reconciliation boundary scoped to Curio loadout widgets.
When item presence changes, it re-enters the existing Character Overview widget
creation hook with a native gadget config, yielding the correct detailed or
empty blueprint. It copies scenegraph placement/index state, retains native
callback names, destroys the prior widget through its own blueprint, and leaves
item icons owned by Darktide. The reverse equipped→empty transition is handled
to prevent a detailed card from persisting after unequip.

Regression coverage in `tests/test_settings.py` uses a plain level-420 Curio,
checks both directions, verifies callback/scenegraph preservation, and proves
that the transition target is the detailed Curio widget rather than a content-
only refresh. `tests/verify.ps1` now requires the reconciliation seam. The
remaining gate is live testing of all Curio slots, including a locked/empty slot,
vanilla item data, custom item data, and immediate return without reopening the
overview.

## Detailed findings

### BI-001 — Manual discard popup can leak global transaction lock

Priority: P1
Confidence: High
Categories: bugs, async, race conditions, feature cohesion, test gap

Status: Implemented in the next-batch remediation. Manual and automatic confirmation popups now retain native popup IDs, lifecycle cleanup removes owned popups, external popup removal is reconciled through `Managers.ui:active_popups()`, and token checks prevent delayed callbacks from affecting a newer transaction. Deterministic coverage includes popup removal without an option callback and stale callback isolation.

Evidence:

- `BetterInventory_features.lua:4426-4458` owns one module-global `discard_transaction`.
- `BetterInventory_features.lua:4492-4505` acquires `owner = "manual"` and releases only through local `clear_pending()`.
- `BetterInventory_features.lua:4507-4554` calls `clear_pending()` only from Confirm, Cancel, or immediate popup-dispatch failure.
- `BetterInventory_features.lua:5676-5678` unregisters an inventory view without releasing a matching manual transaction.
- `BetterInventory.lua:2113-2118` disables the mod but only calls automatic-discard cancellation.

Failure mode:

If engine state transition, view destruction, popup replacement, another mod, or an exceptional UI path closes the confirmation without invoking either option callback, `discard_transaction.owner` remains `"manual"`. Every later manual or automatic discard request is rejected until Lua reload.

Required change:

1. Give each transaction an opaque generation/token and owner view.
2. Add `release_discard_transaction_for_view(view)`.
3. Release matching manual ownership from `unregister_inventory_view`, game-state exit, and `on_disabled`.
4. Hook a reliable popup close/destroy lifecycle if available; do not rely only on button callbacks.
5. Make release idempotent and token-aware so a stale popup cannot release a newer transaction.

Acceptance tests:

- Open manual confirmation, simulate inventory `on_exit` without invoking either option, then open a new view and confirm a new request succeeds.
- Disable mod while manual confirmation is open; re-enable and verify no stale lock.
- Replace popup A with popup B; callback from A must not release B's transaction.
- Existing Confirm/Cancel/missing-dispatch tests continue to pass.

### BI-002 — Sort wrappers survive disable and retain stale closures

Priority: P1
Confidence: High
Categories: bugs, hot reload, memory retention, feature cohesion, architecture

Evidence:

- `BetterInventory_features.lua:3739-3763` replaces each `option.sort_function` and stores `_better_inventory_original_sort`.

The first hotfix added a focused equipment-persistence module around the existing native request, but its authoritative-profile hook introduced a same-session regression: before the outer overview closes, Y exists only as a local preview and no request is active, so a delayed profile event could replace Y with authoritative X. `a4ae5ca` now detects and preserves every uncommitted preview delta. On confirmed persistence it advances the starting snapshot, after which authoritative reconciliation is safe. A pending request is never duplicated; explicit false/error outcomes receive at most two idempotent retries for the same slot/gear set, guarded by account and character identity. Regression coverage now includes the exact X→Y→delayed-X-event→reopen-child transition in addition to pending, false, success, account/character invalidation, bounded failure, and profile reconciliation.

### BI-025 — Same-gear revisions can skip detailed equipped-card refresh

Priority: P2
Confidence: High
Categories: bugs, UI lifecycle, regression coverage

Status: Complete in B26 (`f648c4c`) for the revision markers and regression coverage; B30 adds scoped lifecycle ownership and B34 remains the view-model extraction follow-up. In-game same-gear revision gate not run in this batch.

B5's custom detailed update effectively keys change detection by gear ID. Native code also recognizes a same-gear content update through item name/object changes. BetterInventory can update the base slot while skipping detailed card reconstruction, preserving stale derived fields.

Required change: include revision/content identity, rebuild all variable fields, and test same gear/new object, name, icon, and stat-line changes.

### BI-026 — A pending Curio report can overwrite an earlier report

Priority: P2
Confidence: High
Categories: async, reporting, feature cohesion

Status: Complete for the bounded queue in B32 (`cf8fba2`); scheduler/context diagnostics and domain extraction remain B36. In-game queue/delivery gate not run.

The account state contains one `pending_report`; a later operation overwrites an undelivered result. Required change: use a bounded account-scoped queue or explicit merge policy with stable report IDs, ordered once-only delivery, deduplication, and reload/account-isolation tests.

### BI-027 — Generic failed-module fallback can select unsafe semantics

Priority: P2
Confidence: Medium
Categories: architecture, crash safety, feature cohesion

Status: Complete for typed lookup/invocation and fallback semantics in B33 (`4051b7c`). In-game optional-integration matrix not run.

Every missing module method receives the same false-returning no-op. For the settings registry this can falsely report duplicate registration and suppress conservative dependency refresh. `Contracts.safe_method` also performs method lookup before `pcall`, leaving throwing metamethod lookup outside the boundary.

Required change: use typed per-domain fallback adapters, protect lookup and invocation, and test absent, partial, malformed, and throwing capabilities.

### BI-028 — Rotation pass can consume stale pre-refresh storefront data

Priority: P0 (owner-designated critical hotfix)
Confidence: High
Categories: async, race conditions, purchases, feature correctness

Status: Implemented outside batch numbering in `a5c647b`, `8e6799d`, and `d0d5803`; in-game validation pending.

At the persisted/predicted reset boundary, Darktide's backend can temporarily return the expired storefront. The buyer previously discarded expired boundary metadata, substituted the next wall-clock hour, evaluated that response, and could consume the new rotation before the new offers existed. Depending on timing, this appeared as a premature pass with no purchases, an inconsistent second pass, or a missed set of visibly eligible Curios.

The hotfix passes the prior boundary into every rotation-triggered scan and requires each enabled character storefront to advertise a future boundary strictly beyond it. Stale or metadata-less responses enter a nonterminal five-second synchronization wait; they cannot evaluate offers, emit a false terminal-failure notification, commit the fallback boundary, or consume the real refreshed pass. Rotation-history schema 2 discards schema-1 consumption boundaries that may already have been poisoned, while preserving pending reports and bounded account metadata. Regression coverage proves migration behavior, that the persisted boundary remains unchanged and silent during stale responses, and that purchase proceeds once the backend advertises the advanced rotation.

## Category review

### 1. Bugs

Confirmed or strongly evidenced:

- BI-001 manual transaction lock leak.
- BI-002 persistent comparator mutation.
- BI-004 stale tracked archive.
- BI-009 incomplete live-view disable restoration.
- BI-010 implemented/reporting contract mismatch.
- BI-012 persistence-success assumption.

No deterministic default-path data-loss bug was reproduced by current tests. Destructive candidate selection is generally conservative and revalidated.

### 2. Unguarded crashes

Primary actionable surfaces:

- BI-005 optional-mod direct calls.
- BI-006 layout module load boundary.
- BI-013 equipped/favorite comparator calls.
- Live scenegraph/private-field calls are mostly checked, but capability checks remain duplicated. Centralizing them will reduce future game-update crashes.

### 3. Performance, Lua/RAM allocation, and leaks

Strong controls already present:

- projected-stat and perfect-roll caches use weak keys;
- registered view maps use weak keys;
- rotation history is capped at four accounts;
- retries and diagnostic error text are bounded;
- native icon load/unload/destroy functions are preserved;
- no runtime package loading or custom render-target ownership was found.

Actionable issues:

- BI-007 global per-frame grid scan and `pack_values` allocations.
- BI-008 per-frame signature strings, scenegraph force/query, and unconditional pivot setter.
- BI-011 inert promise graphs can remain until backend settlement.
- BI-019 per-frame string normalization.
- BI-002 stale wrappers retain module/view closures.

Recommended profiling counters:

- active BetterInventory views/panels;
- marked MyFavorites widgets scanned per frame;
- panel rebuild count and reason;
- scenegraph realignment count and reason;
- active async GET/POST operations and oldest age;
- current discard/buyer state and generation;
- Lua GC memory before/after 100 inventory open/close cycles.

### 4. Async nature and race conditions

Good existing design:

- generation tokens invalidate stale continuations;
- storefront scans and purchase POSTs are sequential;
- offers and wallets are re-fetched before purchase;
- automatic discard fetches and revalidates inventory before deletion;
- ambiguous purchase failures are not retried automatically;
- buyer rotation ledger commits before first POST.

Remaining gaps:

- BI-001 popup close lifecycle.
- BI-003 cancellation vs backend-operation ownership.
- BI-010 deferred reporting after menu purchase.
- BI-011 read-only promise ownership/timeout.
- Add explicit account/context snapshot to async operation objects during state-machine refactor, even though current per-frame account check usually invalidates tokens.

### 5. Feature cohesion

Current product has coherent safety defaults, but implementation ownership is fragmented:

- settings are represented in DMF data, main dependency logic, panel builders, localization, docs, and tests;
- sorting spans hooks, features, panels, and optional ItemSorting integration;
- discard and Curio buyer coordinate through one boolean busy API rather than a shared operation arbiter;
- historical docs sometimes describe requirements not reflected in runtime, as in BI-010;
- disabling does not provide one consistent feature teardown contract.

Recommended domain boundaries are described under BI-014 and BI-015.

### 6. Code quality and test coverage level

Assessment: strong deterministic regression volume, medium structural quality, and a useful but incomplete line-coverage baseline.

Strengths:

- 10,410 lines of behavior harnesses and 1,824 assertions;
- malformed item, third-party callback, cancellation, retry, rotation, purchase, delete, packaging, localization, controller, and geometry cases exist;
- current verifier is fast enough for frequent use (about eight seconds in this audit environment).

Gaps:

- CI is present but not self-contained in a clean checkout (BI-022);
- aggregate line coverage exists but is diluted by declarative files, and branch coverage is absent;
- discovery/reporting is script-level rather than named-case level;
- no live engine harness;
- missing cleanup tests identified in BI-001 through BI-003 and BI-009;
- persistence failure mock differs from actual DMF behavior;
- regex verifier impedes extraction.

### 7. Architecture and refactoring opportunities

Highest-value refactors:

1. Explicit operation state machines for discard and buyer.
2. Reversible sorting ownership.
3. Integration/capability adapters.
4. Event/dirty-generation UI updates instead of frame polling.
5. Declarative setting registry.
6. Pure card view-model and geometry modules.
7. Generated localization/settings artifacts.

Avoid a big-bang rewrite. Extract tested seams in the phased plan below.

## Final assessment

BetterInventory has strong safety intent and more deterministic coverage than typical mods of this size. Main threat is now complexity itself: direct mutations and async ownership span large files, while frame hooks and compatibility seams accumulate incrementally. Fix lifecycle ownership first, enforce release artifact parity, then reduce per-frame work. Only after those controls should the codebase be split along domain boundaries.

The project is suitable for gradual AI-agent implementation if agents follow finding IDs, preserve safety invariants, add tests first, and avoid cross-domain rewrites.
