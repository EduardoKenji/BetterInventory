# BetterInventory 2.0.0 full-project audit

Date: 2026-08-07  
Branch: `audit/v2.0.0`  
Baseline: `854ab1c` (`main`)  
Target version: `2.0.0`  
Audit type: static code, architecture, lifecycle, async, performance, test, packaging, and local game-contract review

## Purpose and handoff contract

This document is an implementation backlog, not only a narrative review. It is written so another coding agent can address findings one at a time without rediscovering project context.

For every change:

1. Preserve the fail-closed behavior of discard and purchase workflows.
2. Add or extend a deterministic test before changing high-risk behavior.
3. Run `tests/verify.ps1` after each logical batch.
4. Keep in-game validation separate from deterministic automated acceptance criteria.
5. Do not combine architecture extraction with behavior changes unless the behavior is already covered by tests.
6. Treat Darktide and optional-mod private fields as versioned contracts. Guard them at one adapter boundary.

## Executive summary

The current baseline is unusually well defended for a Darktide Lua mod. Automated verification passes; destructive flows revalidate candidates; Curio purchases are serialized; icon ownership remains native; runtime caches use weak keys where appropriate; rotation history and retries are bounded.

No confirmed unbounded Lua-table leak or BetterInventory-owned render-target leak was found in current source. Main memory risks are stale closures after disable/hot reload, promise graphs retained until backend settlement, and avoidable allocation churn in per-frame hooks.

Release should still be treated as pre-validation. Audit found three high-risk lifecycle/async defects, one release-artifact defect, several unguarded compatibility calls, and substantial refactoring debt:

- Manual discard transaction can remain locked if confirmation closes without either option callback.
- Wrapped sort comparators are not restored on disable and can retain old module closures across hot reload.
- Cancelling automatic discard releases shared transaction ownership even when backend deletion remains in flight.
- Tracked `BetterInventory.zip` was v1.8.0 while source was v1.9.4; current verifier did not notice.
- Global grid and vendor update hooks perform avoidable per-frame allocations/scans.
- `BetterInventory_features.lua`, `BetterInventory_layout.lua`, and `BetterInventory.lua` mix too many responsibilities and contain several 200-500-line functions.
- Test volume was high but initially had no measured Lua coverage, CI workflow, or standard discovery; B16 added these foundations, with clean-checkout portability still open as BI-022.
- Several documented in-game gates remain open, especially hot enable/disable, popup cancellation, controller focus, supported-mod combinations, and Operative Selection notifications.

Independent B1-B20 review supersedes the original release ordering: fix BI-021 through BI-023, establish BI-024 diagnostics, and close BI-025/BI-026 before performance and architecture expansion.

## Detailed findings

### BI-001 — Manual discard popup can leak global transaction lock

Priority: P1
Confidence: High
Categories: bugs, async, race conditions, feature cohesion, test gap

Status: Implemented in the next-batch remediation. Manual and automatic confirmation popups now retain native popup IDs, lifecycle cleanup removes owned popups, external popup removal is reconciled through `Managers.ui:active_popups()`, and token checks prevent delayed callbacks from affecting a newer transaction. Deterministic coverage includes popup removal without an option callback and stale callback isolation.

Evidence:

- `BetterInventory_features.lua:4426-4458` owns one module-global `discard_transaction`.
- `BetterInventory_features.lua:4492-4505` acquires `owner = "manual"` and releases only through local `clear_pending()`.
- `BetterInventory_features.lua:4507-4554` calls `clear_pending()` only from Confirm, Cancel, or immediate popup-dispatch failure.
- `BetterInventory_features.lua:5676-5678` unregisters an inventory view without releasing a matching manual transaction.
- `BetterInventory.lua:2113-2118` disables the mod but only calls automatic-discard cancellation.

Failure mode:

If engine state transition, view destruction, popup replacement, another mod, or an exceptional UI path closes the confirmation without invoking either option callback, `discard_transaction.owner` remains `"manual"`. Every later manual or automatic discard request is rejected until Lua reload.

Required change:

1. Give each transaction an opaque generation/token and owner view.
2. Add `release_discard_transaction_for_view(view)`.
3. Release matching manual ownership from `unregister_inventory_view`, game-state exit, and `on_disabled`.
4. Hook a reliable popup close/destroy lifecycle if available; do not rely only on button callbacks.
5. Make release idempotent and token-aware so a stale popup cannot release a newer transaction.

Acceptance tests:

- Open manual confirmation, simulate inventory `on_exit` without invoking either option, then open a new view and confirm a new request succeeds.
- Disable mod while manual confirmation is open; re-enable and verify no stale lock.
- Replace popup A with popup B; callback from A must not release B's transaction.
- Existing Confirm/Cancel/missing-dispatch tests continue to pass.

### BI-002 — Sort wrappers survive disable and retain stale closures

Priority: P1
Confidence: High
Categories: bugs, hot reload, memory retention, feature cohesion, architecture

Evidence:

- `BetterInventory_features.lua:3739-3763` replaces each `option.sort_function` and stores `_better_inventory_original_sort`.
- Wrapper closes over `mod`, `view`, `Features`, and `original_sort`.
- `BetterInventory_features.lua:5676-5724` unregister/disable paths never restore original comparator or clear marker.
- DMF hook disabling cannot undo direct table mutation.

Status: Implemented in the current remediation batch. Sort ownership is tracked independently of optional panels, disable restores every wrapped live view, re-enable rebinds wrappers, external comparator replacement rebases safely, and deterministic tests cover a GlobalStore view without a native sorting panel.

Impact:

- Sorting priorities can remain active while BetterInventory is disabled.
- Re-enable sees `_better_inventory_original_sort` and does not install a fresh wrapper.
- Hot reload can retain old module tables and code through live sort-option closures.
- Optional ItemSorting replacement after wrapping can leave marker/function ownership inconsistent.

Required change:

1. Add `restore_sort_options(view)` that restores and clears BetterInventory markers only when wrapper ownership matches.
2. Call it on inventory/vendor unregister and before disable cleanup.
3. Re-wrap current options on enable or next setup using a wrapper-generation marker.
4. Detect an external comparator replacement and rebase safely rather than stacking wrappers.
5. Keep original comparator identity tests for ItemSorting and native methods.

Acceptance tests:

- Comparator identity equals original after `disable_inventory_views()`.
- Disabled mod sorts only by native comparator.
- Re-enable installs one fresh wrapper, never two.
- Simulated hot reload does not retain old sentinel module/view closure.
- ItemSorting replacing comparator after first setup is preserved as new base.

### BI-003 — Cancellation unlocks automatic discard before backend delete settles

Priority: P1
Confidence: High
Categories: async, race conditions, destructive workflow, tests

Evidence:

- `BetterInventory_features.lua:4812-4829` keeps transaction ownership until delete promise success/failure during normal completion.
- `BetterInventory_features.lua:4915-4933` cancellation increments token and immediately calls `release_discard_transaction("automatic")`.
- `BetterInventory_features.lua:4571-4576` reports busy only while scheduled or owner is automatic.
- Tests around `tests/test_features.py:2762-2780` assert ownership persists during normal deferred deletion, but do not cancel while that promise is pending.

Status: Implemented in the current remediation batch. Scheduler cancellation now invalidates future scan callbacks without releasing destructive-operation ownership; the busy API remains true through mode changes and mod disable until the delete promise settles. Regression coverage blocks manual entry during deferred deletion and verifies final release.

Failure mode:

Changing mode, disabling feature/mod, or a definitive state exit can release arbitration while `GearService.delete_gear_batch` remains in flight. A new manual flow or Curio Buyer pass can then begin before deletion settles. Token checks prevent stale UI mutation but do not stop the already-dispatched backend request.

Required change:

Separate scheduler cancellation from backend-operation ownership:

- `scheduled/started` may cancel immediately;
- `backend_delete_inflight` remains authoritative until promise settlement;
- cancellation suppresses stale notifications if desired but does not clear shared busy state;
- finalizer releases ownership exactly once.

Acceptance tests:

- Defer delete, cancel, assert busy remains true and manual request remains blocked.
- Curio acquisition receives `automatic_discard_busy = true` until settlement.
- Resolve/reject deferred promise and assert lock releases once.
- Mod disable does not dispatch new work but still finalizes old promise safely.

### BI-004 — Tracked ZIP can be stale while verifier passes

Priority: P1  
Confidence: High  
Categories: bug, release integrity, tests

Evidence:

- `BetterInventory.zip` is tracked by Git.
- At audit start its embedded `MOD_VERSION` was `1.8.0`; source metadata was `1.9.4`.
- `tests/verify.ps1:498-538` generates and validates a temporary archive, then deletes it.
- No check compares tracked `BetterInventory.zip` against source files or version.

Impact:

A release can upload obsolete runtime code despite a green verifier. This is a user-visible release-blocking defect.

Required change — choose one policy:

Preferred:

- remove `BetterInventory.zip` from Git;
- generate versioned archive in CI/release tooling;
- publish SHA-256 from the generated artifact.

Alternative:

- keep it tracked;
- verifier compares every embedded file hash to source and asserts embedded version equals active metadata;
- version bump command rebuilds archive atomically.

Acceptance tests:

- Deliberately alter source after archive build; verifier must fail.
- Deliberately alter embedded version; verifier must fail.
- Archive path and source hashes still satisfy existing packaging invariants.

Status: Implemented in `4ba19e8` and `93129ce`. The verifier compares tracked archive entries to source files, confirms the embedded version, and package cleanup removes failed temporary archives. Final release validation still requires checking the produced artifact and in-game behavior.

### BI-005 — Optional-mod calls can throw through core UI hooks

Priority: P1  
Confidence: High  
Categories: unguarded crashes, integrations, test coverage

Status: Implemented in `ba3ac89`; protected Visible Equipment and Name It boundaries have deterministic throwing-call coverage. Broader adapter centralization remains architecture work.

Evidence:

- `BetterInventory.lua:2368-2369` invokes `visible_equipment_mod:is_enabled()` directly inside widget creation.
- `BetterInventory_item_customization.lua:337` and `:400` invoke Name It's `get` directly while import/reconciliation executes.
- Nearby Equipped Icon+, Lantern, ItemSorting, and most Name It boundaries already use `pcall`, establishing intended isolation policy.

Impact:

One incompatible or partially initialized optional mod can abort Character Overview widget creation or BetterInventory enable/reconciliation.

Required change:

- Introduce small integration adapters: `safe_mod_enabled`, `safe_mod_get`, `safe_mod_call`.
- Return conservative fallbacks and log once per integration/error signature.
- Do not scatter raw third-party method calls through feature code.

Acceptance tests:

- Visible Equipment `is_enabled` throws: native placement widget survives.
- Name It `get` throws during both import and reconciliation: BetterInventory retains internal records and does not crash.
- Errors are bounded/logged once, not every frame.

### BI-006 — Layout module lacks guarded load boundary

Priority: P1  
Confidence: High  
Categories: startup crash, architecture

Status: Implemented in `ba3ac89`; Layout loading is type-checked and logs a clear diagnostic before bootstrap stops. A full native degraded-mode fallback remains intentionally out of scope.

Evidence:

- `BetterInventory.lua:34` loads `Layout` directly.
- `BetterInventory.lua:35-37` wraps Features, CurioAcquisition, and ItemCustomization with `no_op_module`.
- `BetterInventory.lua:43-45` immediately indexes `Layout.set_item_customization_provider`.
- DMF `io_dofile` is protected and can return a non-table after module failure.

Impact:

A syntax/runtime/load error in layout code produces a secondary indexing failure and can prevent the whole mod from loading without the clear degraded-feature behavior used elsewhere.

Required change:

Choose and document one policy:

- Core-fatal: validate `type(Layout) == "table"`, log the original module failure clearly, and stop bootstrap intentionally.
- Degraded pass-through: provide a real layout fallback implementing every called method with native/no-op behavior.

Do not use a generic dynamic no-op for methods where callers expect tables, numbers, or multiple returns.

Acceptance tests:

- Simulated layout load failure produces one clear diagnostic and no secondary `attempt to index` crash.
- If degraded mode is chosen, native inventory/vendor paths still open.

### BI-007 — Global grid update allocates and scans every frame

Priority: P2  
Confidence: High  
Categories: performance, Lua allocation, RAM/GC

Evidence:

- `BetterInventory.lua:2587-2597` hooks every `ViewElementGrid._update_grid_widgets` call.
- It packs native return values into a fresh table through `pack_values`.
- It scans every grid widget and calls `synchronize_myfavorites_marker`, even when MyFavorites is absent and even for unrelated grids.
- Inventory and vendor `update` hooks also allocate `pack_values` tables at `BetterInventory.lua:2214-2223` and `:2257-2271`.
- Local Darktide source confirms update contracts are per-frame; `InventoryWeaponsView.update` returns its superclass result but does not require arbitrary return arity.

Impact:

Avoidable allocation and O(visible widgets) work occurs at frame rate. Cost rises while scrolling or when multiple grid elements are active and creates steady GC pressure.

Required change:

1. Gate MyFavorites synchronization behind detected active integration and marked widgets.
2. Prefer a weak set of widgets carrying BetterInventory/MyFavorites styles.
3. Update on creation, equipped/favorite/loadout change, or a dirty generation; retain a cheap fallback only if no event exists.
4. Remove generic `pack_values` from known update contracts; call native, run post-work, return known values or no values according to source contract.
5. Profile before/after in an inventory with maximum visible cards.

Acceptance tests/benchmarks:

- MyFavorites absent: zero widget-loop calls after setup.
- Unrelated `ViewElementGrid` receives no marker work.
- Integration state change updates marked widgets correctly.
- Add a debug counter for allocations/iterations and verify stable idle frame counts.

### BI-008 — Panel signatures and scenegraph alignment recompute every frame

Priority: P2  
Confidence: High  
Categories: performance, allocations, engine calls

Evidence:

- `BetterInventory_features.lua:2245-2260` creates a parts table, stringifies all sort option names, and concatenates a signature.
- `BetterInventory_features.lua:2584-2607` calls that signature from `panel_structure_key`.
- `BetterInventory_features.lua:3584-3611` recomputes signature and panel position, then calls `set_pivot_offset` every vendor update.
- `BetterInventory.lua:1024-1071` can call `_force_update_scenegraph` and multiple world-position queries.
- `BetterInventory.lua:2257-2268` invokes alignment every CreditsVendorView frame.

Impact:

Idle inventory/vendor views repeatedly allocate strings/tables and force/query scenegraph state even when structure and geometry are unchanged.

Required change:

- Replace polled signatures with monotonic dirty generations updated by setup, sort-option mutation, setting change, selected tab/item change, resize, or integration state change.
- Cache pivot and geometry inputs; call setters only when values differ.
- Move Quick Level Mastery alignment to `on_enter`, grid presentation callback, and explicit dirty events.
- If a low-frequency compatibility poll remains necessary, throttle it (for example 2-4 Hz), not every frame.

Acceptance criteria:

- Idle counters show no signature-table construction and no force-scenegraph call after stabilization.
- ItemSorting enable/disable and option changes still rebuild once.
- Resolution/tab/item changes realign correctly.

### BI-009 — Disable hides controls but does not restore live mutated UI/layout

Priority: P2  
Confidence: High  
Categories: bugs, lifecycle, feature cohesion

Evidence:

- `BetterInventory.lua:2113-2118` delegates disable cleanup.
- `BetterInventory_features.lua:5701-5724` hides panels and clears focus but does not re-present native grids, restore scenegraph definitions, restore comparator wrappers, or remove custom legend actions from already-open views.
- Card blueprints and view definitions are cloned/mutated during presentation throughout `BetterInventory_layout.lua:3124-4159`.
- README explicitly lists hot enable/disable as unvalidated.

Status: Partially implemented in the current lifecycle batch. Disable now restores focused inventory/vendor input ownership, hides custom panels, restores sort wrappers, and removes Armoury legend entries. Full restoration of already-presented card blueprints and geometry still requires a scoped ViewSession extraction and remains open.

Impact:

Disabling while a supported view remains open can leave BetterInventory geometry/cards/comparators/actions alive until view reopen. Re-enable can combine stale view state with fresh hooks.

Required change:

- Define a `ViewSession` cleanup contract per supported view.
- On disable, restore direct mutations, close/re-present using native lifecycle where safe, or close the affected view with an explicit log if native rebuild is unsafe.
- On enable, detect already-open views and initialize once.

Acceptance tests:

- Disable/re-enable in open inventory, Armoury, GlobalStore, Hadron, and Character Overview.
- Native comparator/card/panel/action state is restored without duplicate hooks or widgets.
- Repeat cycle three times and compare widget/pass counts.

### BI-010 — Operative Selection purchase reporting differs from design contract

Priority: P2  
Confidence: High  
Categories: feature cohesion, async, UX, documentation

Status: Implemented in the next-batch remediation. Operative Selection outcomes are stored as bounded account-scoped reports and delivered once when the matching account reaches Morningstar. Automated coverage includes hidden-context persistence, account isolation, and one-time delivery.

Evidence:

- `docs/v1.9.3-automatic-curio-buyer-plan.md:292-293` requires a compact pending report when Operative Selection cannot display the notification.
- At audit baseline, the state table at `BetterInventory_curio_acquisition.lua:87-126` had no pending report.
- At audit baseline, `BetterInventory_curio_acquisition.lua:1670-1685` triggered notification without a deferred handoff.
- The remediation adds a bounded runtime `pending_report` implementation and preserves this baseline evidence for traceability.

Impact:

### BI-024 — Rapid close/reopen can expose stale or failed equip persistence

Priority: P0 (owner-designated critical hotfix)
Confidence: High
Categories: async, race conditions, UI correctness

Status: Implemented outside batch numbering in `4e0497f` and corrected by `a4ae5ca`; in-game validation pending.

Darktide updates local preview synchronously but starts the backend equip request only when the outer Character Overview exits. That request is not awaited by the view. A new view waits at most three seconds and can initialize from stale profile data; its profile-update event does not rebuild equipped items. Backend rejection and late-success/stale-UI currently look identical.

BetterInventory's B5 hook was not on the backend write path, so it was not the original cause. The first hotfix added a focused equipment-persistence module around the existing native request, but its authoritative-profile hook introduced a same-session regression: before the outer overview closes, Y exists only as a local preview and no request is active, so a delayed profile event could replace Y with authoritative X. `a4ae5ca` now detects and preserves every uncommitted preview delta. On confirmed persistence it advances the starting snapshot, after which authoritative reconciliation is safe. A pending request is never duplicated; explicit false/error outcomes receive at most two idempotent retries for the same slot/gear set, guarded by account and character identity. Regression coverage now includes the exact X→Y→delayed-X-event→reopen-child transition in addition to pending, false, success, account/character invalidation, bounded failure, and profile reconciliation.

### BI-026 — A pending Curio report can overwrite an earlier report

### BI-027 — Generic failed-module fallback can select unsafe semantics

### BI-028 — Rotation pass can consume stale pre-refresh storefront data

Priority: P0 (owner-designated critical hotfix)
Confidence: High
Categories: async, race conditions, purchases, feature correctness

Status: Implemented outside batch numbering in `a5c647b`, `8e6799d`, and `d0d5803`; in-game validation pending.

At the persisted/predicted reset boundary, Darktide's backend can temporarily return the expired storefront. The buyer previously discarded expired boundary metadata, substituted the next wall-clock hour, evaluated that response, and could consume the new rotation before the new offers existed. Depending on timing, this appeared as a premature pass with no purchases, an inconsistent second pass, or a missed set of visibly eligible Curios.

The hotfix passes the prior boundary into every rotation-triggered scan and requires each enabled character storefront to advertise a future boundary strictly beyond it. Stale or metadata-less responses enter a nonterminal five-second synchronization wait; they cannot evaluate offers, emit a false terminal-failure notification, commit the fallback boundary, or consume the real refreshed pass. Rotation-history schema 2 discards schema-1 consumption boundaries that may already have been poisoned, while preserving pending reports and bounded account metadata. Regression coverage proves migration behavior, that the persisted boundary remains unchanged and silent during stale responses, and that purchase proceeds once the backend advertises the advanced rotation.

## Category review

### 1. Bugs

Confirmed or strongly evidenced:

- BI-001 manual transaction lock leak.
- BI-002 persistent comparator mutation.
- BI-004 stale tracked archive.
- BI-009 incomplete live-view disable restoration.
- BI-010 implemented/reporting contract mismatch.
- BI-012 persistence-success assumption.

No deterministic default-path data-loss bug was reproduced by current tests. Destructive candidate selection is generally conservative and revalidated.

### 2. Unguarded crashes

Primary actionable surfaces:

- BI-005 optional-mod direct calls.
- BI-006 layout module load boundary.
- BI-013 equipped/favorite comparator calls.
- Live scenegraph/private-field calls are mostly checked, but capability checks remain duplicated. Centralizing them will reduce future game-update crashes.

### 3. Performance, Lua/RAM allocation, and leaks

Strong controls already present:

- projected-stat and perfect-roll caches use weak keys;
- registered view maps use weak keys;
- rotation history is capped at four accounts;
- retries and diagnostic error text are bounded;
- native icon load/unload/destroy functions are preserved;
- no runtime package loading or custom render-target ownership was found.

Actionable issues:

- BI-007 global per-frame grid scan and `pack_values` allocations.
- BI-008 per-frame signature strings, scenegraph force/query, and unconditional pivot setter.
- BI-011 inert promise graphs can remain until backend settlement.
- BI-019 per-frame string normalization.
- BI-002 stale wrappers retain module/view closures.

Recommended profiling counters:

- active BetterInventory views/panels;
- marked MyFavorites widgets scanned per frame;
- panel rebuild count and reason;
- scenegraph realignment count and reason;
- active async GET/POST operations and oldest age;
- current discard/buyer state and generation;
- Lua GC memory before/after 100 inventory open/close cycles.

### 4. Async nature and race conditions

Good existing design:

- generation tokens invalidate stale continuations;
- storefront scans and purchase POSTs are sequential;
- offers and wallets are re-fetched before purchase;
- automatic discard fetches and revalidates inventory before deletion;
- ambiguous purchase failures are not retried automatically;
- buyer rotation ledger commits before first POST.

Remaining gaps:

- BI-001 popup close lifecycle.
- BI-003 cancellation vs backend-operation ownership.
- BI-010 deferred reporting after menu purchase.
- BI-011 read-only promise ownership/timeout.
- Add explicit account/context snapshot to async operation objects during state-machine refactor, even though current per-frame account check usually invalidates tokens.

### 5. Feature cohesion

Current product has coherent safety defaults, but implementation ownership is fragmented:

- settings are represented in DMF data, main dependency logic, panel builders, localization, docs, and tests;
- sorting spans hooks, features, panels, and optional ItemSorting integration;
- discard and Curio buyer coordinate through one boolean busy API rather than a shared operation arbiter;
- historical docs sometimes describe requirements not reflected in runtime, as in BI-010;
- disabling does not provide one consistent feature teardown contract.

Recommended domain boundaries are described under BI-014 and BI-015.

### 6. Code quality and test coverage level

Assessment: strong deterministic regression volume, medium structural quality, and a useful but incomplete line-coverage baseline.

Strengths:

- 10,410 lines of behavior harnesses and 1,824 assertions;
- malformed item, third-party callback, cancellation, retry, rotation, purchase, delete, packaging, localization, controller, and geometry cases exist;
- current verifier is fast enough for frequent use (about eight seconds in this audit environment).

Gaps:

- CI is present but not self-contained in a clean checkout (BI-022);
- aggregate line coverage exists but is diluted by declarative files, and branch coverage is absent;
- discovery/reporting is script-level rather than named-case level;
- no live engine harness;
- missing cleanup tests identified in BI-001 through BI-003 and BI-009;
- persistence failure mock differs from actual DMF behavior;
- regex verifier impedes extraction.

### 7. Architecture and refactoring opportunities

Highest-value refactors:

1. Explicit operation state machines for discard and buyer.
2. Reversible sorting ownership.
3. Integration/capability adapters.
4. Event/dirty-generation UI updates instead of frame polling.
5. Declarative setting registry.
6. Pure card view-model and geometry modules.
7. Generated localization/settings artifacts.

Avoid a big-bang rewrite. Extract tested seams in the phased plan below.

## Final assessment

BetterInventory has strong safety intent and more deterministic coverage than typical mods of this size. Main threat is now complexity itself: direct mutations and async ownership span large files, while frame hooks and compatibility seams accumulate incrementally. Fix lifecycle ownership first, enforce release artifact parity, then reduce per-frame work. Only after those controls should the codebase be split along domain boundaries.

The project is suitable for gradual AI-agent implementation if agents follow finding IDs, preserve safety invariants, add tests first, and avoid cross-domain rewrites.
