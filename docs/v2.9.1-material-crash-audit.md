# BetterInventory v2.9.1 material crash audit

Date: 2026-08-22

## Report and conclusion

FirstFleet reported repeatable crashes while switching weapons from a mission-preparation loadout and from the Psykanium/training context. The available crash summary is:

```text
[Script Error]: scripts/managers/ui/ui_renderer.lua:234:
Error loading material '128'. Reason: 'Material '#ID[9f9992ea9868e120]' not found.'
```

The same material and error shape appeared in two crash reports, including after v2.8.3. No matching full console log or Lua call stack was supplied, so the originating mod and exact assignment cannot be proven from the report alone. The renderer evidence is nevertheless strong enough to identify and contain the failure class.

Darktide texture passes read their material from `ui_content[pass.value_id]`. Passes with `material_values` ask `UIRenderer` to create a GUI material from that value before drawing. `128` is a number, not a material path or material handle, so this fails in engine code before an ordinary Lua error boundary can recover.

The number is also consistent with a render-target atlas grid index being written to the material field by an incompatible callback signature or stale widget update. That is an evidence-based hypothesis, not verified attribution. Native item-icon callbacks receive `grid_index`, `rows`, `columns`, and `render_target`; only the latter values belong in `style.icon.material_values`, while `content.icon` must remain a material reference.

## Vectors reviewed

| Vector | Exposure | v2.9.1 treatment |
| --- | --- | --- |
| Reused BetterInventory inventory card receives a numeric `content.icon` | Direct match for the crash shape | Dynamic texture pass restores its native fallback immediately before `UIPasses` renders it. |
| Native or third-party inventory card is used while BetterInventory grid geometry is disabled | Possible in the same `InventoryWeaponsView` | The created card receives the same one-time pass guard, scoped to the view's primary item grid. |
| Character Overview individual weapon/Curio card is reused after an equipment change | Matches the reported loadout surface | Its final hybrid blueprint is guarded after native lifecycle callbacks and BetterInventory layout changes are composed. |
| Async or compatibility `change_function` rewrites a value after the first check | Possible callback-order race | Validation runs both before and after the delegated change callback. |
| Dynamic wallet, overlay, loading, or inherited texture pass is malformed | Same renderer failure class | Every dynamic texture pass in a BetterInventory-transformed blueprint is guarded, not only the pass named `icon`. |
| Blessing texture helper returns malformed icon/frame metadata | Could corrupt material parameters | Both values must be non-empty strings before card content accepts them. |
| Auto Crafter trait options expose malformed icon/frame metadata | Could corrupt panel material parameters | Non-string values are replaced with the material's empty-texture sentinel. |
| WKC icon resolver returns malformed data | Already protected | Existing integration accepts only a non-empty string and otherwise uses its known static icon. |
| Static BetterInventory texture constants | No mutable value source found | Kept unchanged; packaging verifies the Lua source set, while the game owns the referenced UI resources. |

## Scope and compatibility policy

The remediation does not hook `UIRenderer`, `UIPasses`, or all UI widgets. A global renderer fallback could hide faults in unrelated mods, alter native screens, and add cost to every texture draw. Instead:

- BetterInventory-transformed Inventory, vendor, Hadron, GlobalStore, and Character Overview blueprints guard only their dynamic texture passes;
- native inventory widgets are guarded only when their owner is the primary grid of `InventoryWeaponsView`;
- unrelated training, HUD, mission, lobby, and other-mod widgets pass through unchanged;
- valid non-empty material strings and engine userdata handles are preserved;
- render-target atlas scalars/resources under `style.material_values` are preserved;
- a repair uses the pass's original material and logs at most one warning per widget field.

This covers BetterInventory's plausible contribution without claiming ownership of all material failures in a modded client.

## CPU and memory review

Blueprint guards are installed once during blueprint composition. Their marker makes repeated composition and runtime card creation idempotent. Native inventory cards receive at most one small closure per dynamic texture pass, owned and released with that widget.

On a valid draw, the guard performs bounded type checks and allocates no tables or strings. There is no inventory scan, renderer-wide hook, timer, registry, strong view reference, or idle update. Warning state is one boolean created only after an invalid value is observed. The module retains no widgets, views, materials, or render targets.

## Regression evidence

The v2.9.1 behavior suite discovers 42 test files and 164 named cases. The critical material case proves that:

- numeric `128`, nil, and table values are repaired to a known native fallback;
- valid custom material strings remain unchanged;
- a delegated callback that writes `128` is repaired after it returns;
- repeated corruption produces no warning storm;
- render-target `grid_index`, `rows`, and `columns` remain unchanged;
- blueprint and runtime guards are idempotent;
- unrelated views are not guarded;
- no global renderer/pass hook was introduced.

The existing equipment, deferred-sort, character-switch, view-lifecycle, DMF/Alf, Auto Crafter, Curio, discard, WKC, layout, and packaging cases remain part of the full suite.

## Remaining live-validation limit

The fix prevents this invalid value from reaching the material loader on BetterInventory-owned surfaces, but a real FirstFleet console log is still needed to verify which callback or mod originally supplied `128`. If a future crash survives v2.9.1, collect the complete console log and installed mod list. The one-time warning beginning `Repaired invalid UI material` will identify the affected dynamic field and distinguish a successfully contained bad assignment from an unrelated renderer/resource failure.
